## 2. 核心原则

- 单一事实源：需求点追溯只在本仓登记，服务仓不复制
- 跨服务契约只能在本仓修改，服务仓经 `sdd/` 只读消费
- 本仓文件随 feature 分支变更，分支名与各服务相同：`feature/<需求目录名>`

## 3. AI 安全约束

<!-- 红线，禁止降级、禁止删除。 -->

- 禁止在本仓存放任何密钥、凭证、生产配置
- 禁止在本仓存放服务仓的私有 Spec 或业务代码
- AI 修改本仓文件必须走 MR，禁止直推

## 目录

| 路径 | 内容 |
|---|---|
| `repos.yaml` | 仓清单：服务仓地址、域、多仓豁免理由 |
| `domains.yaml` | 域清单：域 → 归属仓 |
| `prd-index.md` | 需求追溯索引（source: workitem） |
| `spec.md` | 主 spec：FEAT 映射表 + 能力索引，不写功能需求正文 |
| `spec-contract-<主题>.md` | 跨服务契约 |
| `changes/<需求目录>/` | 跨服务需求的全局 spec.md 和 design.md |
| `changes/archive/<年份>/` | 已归档的跨服务需求 |

## 工作方式

- 跨服务需求：`/sdd-grill` 在本仓创建 `changes/<需求目录>/` 并登记 prd-index；全局 spec 评审通过后，各服务仓才开始实现。
- FEAT 编号在本仓分配，项目内唯一；FR 的新增、修改、删除随服务仓的 MR 同步本仓 `spec.md` 的 FEAT 映射表。
- 本仓的 MR 与各服务仓的 MR 同名 feature 分支；归档时一起移到 `changes/archive/<年份>/`。
