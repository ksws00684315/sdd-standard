# 第一部分　方案概要

## 1. 背景与问题

本团队的现状：

- 系统由多个 Spring Boot 微服务组成，每个服务是独立的 git 仓库，托管在 GitLab 上。
- 开发者普遍使用 AI 编码工具，但各人使用的工具不同。习惯做法是把所有服务放在同一个目录下，作为 AI 工具的工作空间。
- 需求由自建系统统一编号，接口契约维护在接口文档平台上。

在这种现状下，AI 编码放大了三个问题：

| 问题 | 表现 |
|---|---|
| **需求理解偏差** | 需求以一句话交给 AI，AI 自行补全大量假设；偏差往往到评审甚至上线后才被发现 |
| **AI 输出难以把控** | 一次生成的改动量大，评审时缺少"应该做成什么样"的对照标准 |
| **决策散落、跨服务协调靠口头** | 需求细节和设计决策留在聊天记录和个人会话里，换人、换会话就丢失；跨服务需求的调用顺序、上线顺序没有统一记录 |

## 2. 方案概要

针对上述问题，方案采用 SDD（Spec-Driven Development，规格驱动开发）的做法：先把"要做什么"写成规格（spec）并评审，再由人或 AI 按规格实现。

**一句话**：在不改变现有仓库结构和工具链的前提下，为每个需求建立"先写 spec、评审通过、再按 spec 实现"的流程；spec 与代码放在同一个服务仓库、同一个 MR 里评审和合并；用一组统一分发的 AI 技能（skill），让不同的 AI 工具都按同一套流程工作。

方案由五个部分组成：

1. **规则仓库**：把现有的工作空间目录本身作为一个 git 仓库，集中管理规范、AI 规则、技能和模板。服务仓库保持独立，不受影响。
2. **服务仓库中的 spec 体系**：每个服务新增两类文档。变更 spec 描述"这次要改什么"，随需求产生、上线后归档；现状规格描述"系统现在是什么样"，随代码长期维护。跨服务需求由一个主服务承载完整的 spec。
3. **按改动大小分三档**：bug 修复等小改动（L0）不需要写 spec；单服务功能（L1）写一份 spec；跨服务、接口或表结构变更（L2）写完整的 spec、设计和任务拆分。
4. **三道质量关**：写代码前做 spec 评审；每个任务完成后由 AI 做两轴自审（编码规范、是否符合 spec）；合并前做代码评审。
5. **AI 技能支撑**：12 个技能覆盖需求澄清、写 spec、拆任务、测试先行实现、审查、排查疑难 bug 等环节，通过规则仓库统一分发，`git pull` 即可更新。

## 3. 预期收益

| 收益 | 实现方式 | 试点期怎么度量 |
|---|---|---|
| 需求偏差在写代码前暴露 | AI 按决策树逐轮追问，每个问题附推荐答案；spec 必须列出"不做什么"和可测试的验收条件 | spec 评审中发现的问题数；上线后因需求理解偏差导致的缺陷数 |
| AI 输出可评审、可对照 | 每条需求编号、可写成测试；任务拆成可以单独验证的小切片；评审有明确的检查项 | 代码 MR 被打回的次数 |
| 决策可追溯 | 需求、设计、跨服务的上线顺序、关键决策都留在仓库里，和代码一起版本化 | 定期抽查 spec 与代码行为的一致性 |
| 不同 AI 工具行为一致 | 统一的规则入口和技能，不绑定某一个工具 | 试点中至少覆盖两种 AI 工具 |

以上收益在试点期按"度量方式"一列收集数据，作为是否全面推广的依据。

## 4. 成本与影响

| 对象 | 影响 |
|---|---|
| 开发者 | L1、L2 需求在写代码前增加编写 spec 和评审的时间，主要由 AI 起草、人确认；L0 改动基本没有额外负担。具体耗时在试点中实测 |
| 服务仓库 | 新增 `docs/specs/`、`docs/changes/` 两个目录和一份 MR 模板，不改动代码结构 |
| 评审人 | 新增一次 spec 评审，在 GitLab 的 Draft MR 上完成 |
| 工具与系统 | 不引入新系统。复用 GitLab、自建需求系统、接口文档平台；AI 工具不限定品牌 |
| 维护 | 规则仓库需要一名规范负责人，规范的修改通过 MR 由架构师评审 |

## 5. 推进计划

| 阶段 | 时长 | 内容 | 进入下一阶段的条件 |
|---|---|---|---|
| 0 准备 | 约 1 周 | 确认第三部分的事项；补齐服务地图、编码规范、需求单号格式；接入试点涉及的服务 | 规范 v0.1 确认，试点人员完成上手 |
| 1 试点 | 2～3 周 | 1～2 人完成 1 个 L2 需求和 1～2 个 L1 需求，每个需求完成后复盘 | 根据复盘修订出 v0.2 |
| 2 小组推广 | 约 1 个月 | 一个小组的所有 L1、L2 需求按规范执行 | 评估指标没有明显恶化，小组认可，发布 v1.0 |
| 3 全团队 | 持续 | 所有服务接入，MR 模板的检查项作为合并条件 | — |

试点期间有 8 项规则按默认做法执行并记录观察结果，试点结束时逐项给出结论（见附录 A 中的试点与推广计划）。

## 6. 主要风险与应对

| 风险 | 应对 |
|---|---|
| 流程过重，团队抵触 | 按改动大小分档，L0 不写 spec；先试点再推广，试点期专门观察流程负担 |
| spec 与代码逐渐脱节 | spec 与代码在同一个 MR 里合并；MR 模板有对应的检查项；AI 自审时检查现状规格是否同步 |
| AI 不按流程执行 | 各阶段由开发者输入命令显式触发，不依赖 AI 自行判断；评审结论始终由人做出 |
| 不同 AI 工具的支持程度不同 | 规则统一写在各工具都能读取的 `AGENTS.md` 里；工具不支持技能时，可以让 AI 直接读技能文件并照着执行 |
| 跨服务需求协调成本高 | 主服务承载完整的 spec 和上线顺序；任务依赖可以跨服务标注，并和上线顺序保持一致 |

# 第二部分　设计说明

## 7. 总体架构

```
┌─ 规则仓库（即 AI 工作空间根目录）─────────────────────────────┐
│  规范文档 · AGENTS.md（AI 规则入口）· 技能 · 模板 · 脚本          │
│                                                                │
│  ├─ order-service/        独立 git 仓库，不受规则仓库版本控制     │
│  │    └─ docs/specs/  docs/changes/    ← spec 存放于此           │
│  ├─ inventory-service/    同上                                  │
│  └─ ...                                                        │
└────────────────────────────────────────────────────────────────┘
```

| 组成 | 职责 | 维护方 |
|---|---|---|
| 规则仓库 | 规范、AI 规则、技能、模板、服务地图、术语表索引、跨服务架构决策 | 规范负责人；修改走 MR，由架构师评审 |
| 服务仓库 | 变更 spec、现状规格、服务术语表、服务内架构决策 | 需求负责人、服务负责人 |
| AI 工具 | 在工作空间根目录打开，读取规则入口；使用统一分发的技能 | 开发者个人，技能由规则仓库统一更新 |

规则仓库用 `.gitignore` 白名单只跟踪自身文件，服务仓库 clone 在其中但互不干扰，不使用 submodule。

**与现有系统的衔接**

| 现有系统 | 在方案中的角色 |
|---|---|
| GitLab | 托管规则仓库和服务仓库；spec 评审在 Draft MR 上进行；MR 模板承载检查项 |
| 自建需求系统 | 需求单号贯穿需求目录名、分支名、commit 和 MR |
| 接口文档平台 | 接口字段明细的唯一来源；spec 和设计文档只写接口变更要点和兼容性 |
| AI 编码工具 | 不限品牌。统一读取 `AGENTS.md`，支持技能的工具直接使用技能 |

## 8. spec 体系

完整规则见附录 A 中的《服务仓库 spec 管理规范》。

### 8.1 两类 spec

| 类型 | 回答的问题 | 位置 | 生命周期 |
|---|---|---|---|
| 变更 spec | 这次要改什么 | `docs/changes/<需求目录>/` | 随需求产生；上线后归档到 `archive/<年份>/`，之后只修正错别字和链接 |
| 现状规格 | 系统现在是什么样 | `docs/specs/<业务能力>.md` | 长期存在；以主干为准，随代码同一个 MR 合并 |

现状规格按业务能力拆分文件，例如"订单状态流转""库存锁定与释放"，并配一个索引。每份现状规格末尾有变更记录，列出哪些需求改过这块能力。

### 8.2 变更 spec 的组成

| 文件 | 内容 | 什么时候需要 |
|---|---|---|
| `spec.md` | 背景、范围、不做什么、编号的验收条件（EARS 句式）、非功能要求、测试接缝、变更记录 | L1、L2 |
| `design.md` | 服务影响矩阵、接口变更要点、数据变更、关键流程、关键决策、上线顺序与回滚、风险 | L2 |
| `tasks.md` | 按垂直切片拆分的任务，每个任务写明交付的行为、覆盖的需求、阻塞依赖 | L2；L1 一次做不完时 |

验收条件采用 EARS 句式，例如：`WHEN 订单处于待支付且超过 30 分钟，THE SYSTEM SHALL 把订单改为已取消`。每条都能直接写成测试。

### 8.3 跨服务需求：主服务模型

- 由需求发起方或核心服务担任**主服务**，承载完整的 `spec.md`、`design.md` 和本服务的 `tasks.md`。
- 其他涉及的**参与服务**只放本服务的 `tasks.md`，用 `<主服务名>:<需求目录名>` 引用主服务的 spec。这个引用不受分支和归档位置影响。
- 任务编号在整个需求内统一，依赖可以跨服务标注，例如"order-service T4 被 inventory-service T1 阻塞"，并且和设计中的上线顺序保持一致。
- 各服务使用同名的 feature 分支，各自提 MR。

### 8.4 状态与职责

```
草稿 ─► 评审中 ─► 已确认 ─► 已上线
                         └─► 已中止
```

- 状态只记录在主服务的 `spec.md` 里。实现进度通过各服务 `tasks.md` 的勾选情况体现。
- **需求负责人**（每个需求一人）：维护该需求在所有服务里的变更 spec，推进状态，负责归档。
- **服务负责人**：对本服务现状规格的准确性负责。
- **MR 作者**：在 MR 里同步更新现状规格。

### 8.5 关键规则

- **现状规格以主干为准**：规则随代码合并进主干时写入，不等上线。被功能开关关闭的规则也要写，并注明开关名。
- **更新义务**：任何改变业务行为的 MR，都要更新对应能力已有的现状规格，包括 L0。L1、L2 改到还没有现状规格的能力时，先补写。
- **评审通过后的需求变化**：先改 spec，追加变更记录，再请评审人重新确认。
- **存量文档**：已有的需求和设计文档不迁移。第一次改到某块能力时，再补写它的现状规格，并链接旧文档。
- **命名**：文件名、目录名用英文，内容用中文。需求目录名为 `<需求单号>-<英文短描述>`，分支名为 `feature/<需求目录名>`。

## 9. 分档与流程

### 9.1 分档

| 档位 | 场景 | 需要的文档 |
|---|---|---|
| L0 | bug 修复、小调整、配置变更 | 不需要 spec；补测试，并更新已有的现状规格 |
| L1 | 单服务内的新功能或行为变化 | `spec.md` |
| L2 | 跨服务需求、接口变更、表结构变更 | 主服务：`spec.md` + `design.md` + `tasks.md`；参与服务：`tasks.md` |

拿不准时按高一档处理。

### 9.2 流程

```
① 需求澄清 → ② 写 spec → ③ 拆任务 → ④ spec 评审 → ⑤ 实现 → ⑥ 代码评审与合并 → ⑦ 归档
└───────── 同一个 AI 会话 ─────────┘              └ 每个任务一个新会话 ┘
```

| 阶段 | 执行方 | 产出 | 完成标准 |
|---|---|---|---|
| ① 需求澄清 | AI 提问，开发者决策 | 档位、主服务、共识 | 没有未决问题，开发者确认共识 |
| ② 写 spec | AI 起草，开发者确认 | `spec.md`，L2 加 `design.md` | 测试接缝已确认；每条需求可测试；没有待确认问题 |
| ③ 拆任务 | AI 起草，开发者确认 | 各服务的 `tasks.md` | 每条需求都被任务覆盖；粒度和依赖已确认 |
| ④ spec 评审 | 评审人 | 所有 Draft MR 通过，状态改为"已确认" | spec 评审检查项全部通过 |
| ⑤ 实现 | AI 实现，开发者把关 | 代码、测试、更新后的现状规格 | 测试通过；自审问题已处理 |
| ⑥ 代码评审与合并 | 评审人 | 合并到主干 | 代码评审检查项全部通过 |
| ⑦ 归档 | 需求负责人 | 变更 spec 移入归档目录 | 上线后两周内完成 |

**上下文要求**：①②③ 在同一个 AI 会话里连续完成，让 spec 直接建立在原始讨论上。⑤ 每个任务开一个新会话，只凭 spec 和任务描述工作，避免上下文混杂。

## 10. 质量门禁

| 关口 | 时机 | 检查内容 | 落地方式 |
|---|---|---|---|
| spec 评审 | 写代码前 | "不做"清单明确；每条需求可测试；测试接缝合理；没有待确认问题；L2 再看影响矩阵、上线顺序、回滚方案，以及任务依赖是否和上线顺序一致 | Draft MR 和 MR 模板里的检查项 |
| 测试先行 | 实现中 | 在确认过的接缝上先写失败的测试，再写实现；只 mock 服务边界之外的依赖 | 实现技能内置；AI 自审时检查 |
| 两轴自审 | 每个任务完成后 | **Standards**：是否符合编码规范，外加一组通用的代码坏味道基线。**Spec**：漏做的需求、范围蔓延、实现错误、现状规格没同步。两轴分开报告 | 审查技能，由实现技能自动调用 |
| 代码评审 | 合并前 | 对照 spec 和 MR 自查项，重点看业务正确性和上线风险 | MR 模板里的检查项 |

试点期的评审人建议：L1 由服务负责人评审，L2 再加上架构师（见第 14 节 D5）。

## 11. 领域模型治理

- **术语表**：每个服务一份 `GLOSSARY.md`，一个业务概念只保留一个用词。规则仓库的 `GLOSSARY-MAP.md` 汇总各服务的术语表，并记录服务之间的术语对应关系。术语冲突在需求澄清阶段当场确定。
- **架构决策记录（ADR）**：同时满足"难以撤销""没有上下文会让人意外""确实经过取舍"三个条件才写，一段话即可。跨服务的决策放在规则仓库，服务内部的决策放在服务仓库。
- spec 或代码和已有 ADR 冲突时，必须明确提出，不能悄悄推翻。

## 12. AI 技能支撑

### 12.1 技能清单

| 类别 | 技能 | 触发方式 | 作用 |
|---|---|---|---|
| 阶段 | `sdd-grill` | 开发者输入命令 | 判断档位、创建分支、澄清需求 |
| | `sdd-spec` | 同上 | 确认测试接缝，编写 spec 和设计 |
| | `sdd-tasks` | 同上 | 拆分垂直切片任务，标注依赖 |
| | `sdd-implement` | 同上 | 一次实现一个任务，完成后自审并提交 |
| 方法 | `sdd-interview` | 被阶段技能调用，也可单独使用 | 按决策树逐轮提问，每个问题附推荐答案 |
| | `sdd-domain` | 同上 | 维护术语表和 ADR |
| | `sdd-tdd` | 同上 | 测试先行开发，附 Java 正反例 |
| | `sdd-review` | 同上 | 两轴审查 |
| | `sdd-diagnose` | 同上 | 疑难 bug 和性能退化的诊断 |
| 工具 | `sdd-questionnaire` | 开发者输入命令 | 把需要产品或业务方决定的问题整理成问卷 |
| | `sdd-handoff` | 同上 | 换工具或转交同事时生成交接文档 |
| | `sdd-retro` | 同上 | 需求完成后复盘，提出规则和模板的改进建议 |

### 12.2 设计原则

- **阶段技能由人显式触发**，方法技能被阶段技能调用。流程走到哪一步，由开发者决定。
- **每种方法只在一个技能里定义**，阶段技能通过调用复用，避免同一规则在多处出现、互相矛盾。
- **AI 负责起草和实现，结论由人做出**：档位、主服务、spec 内容、任务拆分都要开发者确认；评审结论由评审人做出。

### 12.3 分发与兼容

- 技能放在规则仓库里，由脚本软链到个人的技能目录；更新只需 `git pull`。
- 规则统一写在 `AGENTS.md` 里，主流 AI 工具都会读取；Claude Code 通过 `CLAUDE.md` 引用它。
- 工具不支持技能，或不支持技能之间的调用时，让 AI 直接读对应的技能文件并按步骤执行。

## 13. 关键设计取舍

| 议题 | 备选方案 | 选择 | 理由 |
|---|---|---|---|
| spec 放在哪 | 集中在规则仓库 / 分散到服务仓库 | 服务仓库 | spec 和代码在同一个 MR 里评审合并，生命周期一致，最不容易脱节 |
| 跨服务需求的整体信息 | 每个服务各写一份 / 放在需求系统 / 由主服务承载 | 主服务承载 | 只有一份完整的 spec，不会出现多份不一致；参与服务通过引用获取 |
| 流程框架 | 采用现成的开源 SDD 框架 / 自定义轻量规范 | 自定义 | 现成框架大多默认单仓库，并且接管整个流程，不适合多仓库微服务和多种 AI 工具并存的现状 |
| 流程强度 | 所有改动走同一套流程 / 按改动大小分档 | 分档 | 小改动走完整流程收益低、阻力大 |
| 工作空间 | 新建独立的规范仓库 / 工作空间目录本身作为规则仓库 | 工作空间即规则仓库 | 符合现有使用习惯，AI 打开工作空间即可读到规则，不需要 submodule |
| 阶段触发 | AI 自动判断 / 开发者输入命令 | 开发者输入命令 | 流程走向可控，不依赖 AI 的判断是否稳定 |
| 状态粒度 | 包含"实现中"等细粒度状态 / 只记录关键节点 | 只记录关键节点 | 状态集中在主服务，参与服务实现时不需要跨仓库修改状态；进度看任务勾选 |
| 现状规格口径 | 以上线为准 / 以主干为准 | 以主干为准 | 和"随代码同一个 MR 合并"的机制一致，不需要上线后再补一次 |
| 存量文档 | 接入时集中迁移 / 改到哪块补哪块 | 改到哪块补哪块 | 降低接入门槛，补写的内容一定是当前在用的 |

## B. 术语

| 术语 | 含义 |
|---|---|
| 变更 spec | 描述一次需求要改什么的文档，包括 `spec.md`、`design.md`、`tasks.md` |
| 现状规格 | 描述系统当前业务行为的文档，按业务能力组织 |
| 主服务 / 参与服务 | 跨服务需求中，承载完整 spec 的服务 / 其他涉及的服务 |
| EARS | 一种需求句式：`WHEN <条件>，THE SYSTEM SHALL <行为>`，便于直接转成测试 |
| 测试接缝 | 测试所站的公共边界，例如 HTTP 接口、对外的 Service 接口、MQ 消费入口 |
| 垂直切片 | 贯穿所需各层、交付一段完整可验证行为的任务，与"按层拆分"相对 |
| 两轴自审 | 从编码规范（Standards）和 spec 符合度（Spec）两个方向分别审查代码 |
| ADR | 架构决策记录（Architecture Decision Record） |
