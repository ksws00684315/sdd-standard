# 团队 SDD 规范方案总览

- 版本：v0.1（试点版）
- 用途：一页看懂整套方案，适合给架构师、负责人和新成员快速了解
- 说明：本文是摘要，具体规则以各专项文档为准，文中给出了对应链接；两者不一致时，以专项文档为准

## 1. 要解决的问题

公司要求团队按 SDD（Spec-Driven Development，规格驱动开发）规范编码。团队的现状是：

- 多个 Spring Boot 微服务，每个服务是独立的 git 仓库
- 大家把所有服务放在同一个目录里，用这个目录作为 AI 工具的工作空间
- 每个人用的 AI 工具不一样
- 用 GitLab 托管代码，需求由自建系统统一编号，接口契约放在接口文档平台上

SDD 要解决三个问题：**需求理解偏差**、**AI 输出不可控**、**决策丢失**。为此遵守三条原则：

- **先对齐，再动手**
- **spec 是事实来源**：实现必须偏离 spec 时，先改 spec
- **按改动大小分档**：小改动不走重流程

## 2. 总体架构：三层

```
┌─ 规则仓库（= 工作空间目录本身，一个 git 仓库）──────────────────┐
│  规范文档 · AGENTS.md · 12 个 sdd skill · 模板 · 脚本           │
│  不存放真实需求的 spec                                          │
│                                                                 │
│  ├─ order-service/      ← 独立 git 仓库，被 .gitignore 白名单排除 │
│  │    └─ docs/specs/ + docs/changes/   ← 所有 spec 放在这里       │
│  └─ inventory-service/  ← 同上                                  │
└─────────────────────────────────────────────────────────────────┘
        ▲ AI 工具在工作空间根目录打开，读 AGENTS.md
        ▲ skill 软链到个人目录，git pull 即可更新
```

| 层 | 放什么 | 由谁维护 |
|---|---|---|
| 规则仓库 | 规则、skill、模板、服务地图、术语表索引、跨服务 ADR | 规范负责人，修改走 MR，由架构师评审 |
| 服务仓库 | 变更 spec、现状规格、服务术语表、服务内 ADR | 需求负责人、服务负责人 |
| AI 工具层 | AGENTS.md 规则入口和 skill | 通过规则仓库统一分发 |

│   ├── spec-management.md    服务仓库 spec 管理规范

│   ├── rollout-plan.md       试点与推广计划

## 4. 服务仓库的 spec 管理

详见[服务仓库 spec 管理规范](spec-management.md)。

### 4.1 两类 spec

| 类型 | 回答的问题 | 位置 | 生命周期 |
|---|---|---|---|
| 变更 spec | 这次要改什么 | `docs/changes/<需求目录>/` | 随需求产生，上线后归档，归档后只修正错别字和链接 |
| 现状规格 | 系统现在是什么样 | `docs/specs/<能力>.md` | 长期存在，**以主干为准**，随代码一起合并 |

### 4.2 目录

```
docs/
├── specs/       README.md 索引 + 每个业务能力一个文件
├── adr/         服务内部的决策（需要时创建）
└── changes/
    ├── REQ-12345-order-timeout-cancel/   进行中的需求
    └── archive/2026/                     已上线或已中止的需求，按年份分组
```

### 4.3 命名

- 文件名、目录名用英文小写加连字符，标题和正文用中文。
- 需求目录名 = `<需求单号>-<3～5 个英文单词>`，分支名 = `feature/` + 需求目录名。

### 4.4 跨服务需求

- 主服务放完整的 `spec.md`、`design.md` 和本服务的 `tasks.md`。
- 参与服务只放本服务的 `tasks.md`，用 `order-service:REQ-12345-...` 的格式引用主服务 spec。spec 移进归档目录后，这个引用照样能找到。

### 4.5 状态

状态只记录在主服务的 `spec.md` 里：

```
草稿 ─► 评审中 ─► 已确认 ─► 已上线
                         └─► 已中止
```

实现进度看各服务 `tasks.md` 的勾选情况，不另设状态。

### 4.6 职责

- **需求负责人**：每个需求一人，维护它在所有涉及服务里的变更 spec，推进状态，负责归档。
- **服务负责人**：对本服务现状规格的准确性负责。
- **MR 作者**：在 MR 里同步更新现状规格。

### 4.7 更新规则

- 任何改变业务行为的 MR，都要在同一个 MR 里更新对应能力已有的现状规格，并追加变更记录。这条包括 L0。
- L1、L2 改到的能力还没有现状规格时，先补写。L0 遇到这种情况，试点期只需在 MR 里注明。
- 评审通过后需求有变化：先改 spec，追加变更记录，再请评审人重新确认。
- 多个需求同时修改同一个能力：以主干为准，按代码冲突的方式合并。

### 4.8 归档和存量文档

- **归档**：所有服务上线后，状态改为"已上线"，用 `git mv` 移到 `archive/<年份>/`。上线后两周内完成，可以顺带放在下一个 MR 里。
- **存量文档**：不迁移。第一次改到某个能力时补写它的现状规格，并在"参考资料"里链接旧文档。

## 5. 分档

| 档位 | 场景 | 文档 | 流程 |
|---|---|---|---|
| L0 | bug 修复、小调整、配置变更 | 无 | 直接修改，补测试；疑难 bug 用 `sdd-diagnose` |
| L1 | 单服务内的新功能或行为变化 | `spec.md`（一次会话做不完时加 `tasks.md`） | `/sdd-grill` → `/sdd-spec` → Draft MR → `/sdd-implement` |
| L2 | 跨服务需求、接口变更、表结构变更 | 主服务三份文档，参与服务各一份 `tasks.md` | `/sdd-grill` → `/sdd-spec` → `/sdd-tasks` → Draft MR → 每个任务一次 `/sdd-implement` |

拿不准时按高一档处理。详见[规范正文](standard.md)第 4 节。

## 6. 流程

```
① 需求拷问 → ② 写 spec → ③ 拆任务 → ④ Draft MR 评审 → ⑤ 实现 → ⑥ 合并 → ⑦ 归档
└───────── 同一个会话 ─────────┘                 └ 每个任务一个新会话 ┘
```

| 阶段 | 命令 | 产出 | 完成标准 |
|---|---|---|---|
| ① 需求拷问 | `/sdd-grill` | 档位、主服务、feature 分支、共识；更新的术语表和 ADR | 决策树里没有未决问题，开发者确认共识 |
| ② 写 spec | `/sdd-spec` | `spec.md`，L2 加 `design.md` | 测试接缝已确认；每条需求有编号且可测试；没有待确认问题 |
| ③ 拆任务 | `/sdd-tasks` | 各服务的 `tasks.md` | 每条需求都被覆盖；粒度和依赖已确认 |
| ④ 评审 | 人工 | 所有 Draft MR 通过后，状态改为"已确认" | spec 评审检查项全部通过 |
| ⑤ 实现 | `/sdd-implement` | 代码、测试、更新后的现状规格 | 测试通过；两轴审查的问题已处理；已提交 |
| ⑥ 合并 | 人工 | 合并到主干 | 代码评审检查项全部通过 |
| ⑦ 归档 | 人工 | 移到 `archive/<年份>/` | 上线后两周内完成 |

核心做法：

- 需求用 EARS 句式，每条编号：`WHEN <条件>，THE SYSTEM SHALL <行为>`。
- spec 必须有"不做"一节和测试接缝。
- 任务按**垂直切片**拆：每个任务交付一段完整、可以单独验证的行为，一次会话能做完。预重构排在最前，依赖可以跨服务，并且和上线顺序一致。
- 实现**测试先行**：在确认过的接缝上，一次写一个失败的测试，再写刚好让它通过的代码。只 mock 服务边界之外的依赖。

详见[规范正文](standard.md)第 5 节和[完整示例](example/REQ-0000-order-timeout-cancel/README.md)。

## 7. 评审

| 环节 | 时机 | 内容 |
|---|---|---|
| spec 评审 | 写代码之前 | 每个服务开一个 Draft MR，按检查项评审：不做清单、可测试性、测试接缝、待确认问题，L2 再看影响矩阵和上线顺序 |
| 两轴审查 | 每个任务完成后，由 AI 执行 | **Standards**：编码规范加 Fowler 坏味道基线。**Spec**：漏做的需求、范围蔓延、实现错误、现状规格没同步。两轴分开报告 |
| 代码评审 | 合并之前 | reviewer 对照 spec 和 MR 自查项，重点看业务正确性和上线风险 |

- spec 和代码在同一个分支、同一个 MR 里合并。
- 试点期的评审人建议：L1 由服务负责人评审，L2 再加上架构师。

## 8. 术语表与 ADR

- 每个服务一份 `GLOSSARY.md`，一个概念只保留一个用词；需求拷问中发现术语冲突时，当场确定并写入。
- ADR 同时满足"难以撤销""没有上下文会让人意外""确实经过取舍"三个条件才写，一段话即可。跨服务决策放规则仓库，服务内部决策放服务仓库。
- 和已有 ADR 冲突时必须明确指出。

## 9. Git 约定

- 分支：`feature/<需求单号>-<描述>`；修复用 `fix/`，L0 没有需求单号时用 `fix/<描述>`。同一需求在各服务用相同的分支名。
- commit：Conventional Commits，有需求单号时带上。
- MR：使用服务仓库的 MR 模板。规则仓库的改动单独提 MR。

## 10. AI 工具层：12 个 skill

| 类别 | skill | 触发方式 | 作用 | 改写自 |
|---|---|---|---|---|
| 阶段 | `sdd-grill` | 人工输入命令 | 判断档位、创建分支、拷问需求 | grill-with-docs |
| | `sdd-spec` | 人工 | 确认测试接缝，写 spec 和 design | to-spec |
| | `sdd-tasks` | 人工 | 拆垂直切片，标注依赖 | to-tickets |
| | `sdd-implement` | 人工 | 一次实现一个任务，完成后审查并提交 | implement |
| 方法 | `sdd-interview` | AI 自动调用，也可单独使用 | 多轮决策树提问 | grilling |
| | `sdd-domain` | 同上 | 维护术语表和 ADR | domain-modeling |
| | `sdd-tdd` | 同上 | 测试先行，附 Java 正反例 | tdd |
| | `sdd-review` | 同上 | 两轴审查 | code-review |
| | `sdd-diagnose` | 同上 | 疑难 bug 诊断，加入了 Arthas、JFR 等 Java 工具 | diagnosing-bugs |
| 工具 | `sdd-questionnaire` | 人工 | 把需要产品方决定的问题整理成问卷 | to-questionnaire |
| | `sdd-handoff` | 人工 | 换工具或转交同事时生成交接文档 | handoff |
| | `sdd-retro` | 人工 | 复盘，改进规则和模板 | retro |

- **调用关系**：`sdd-grill` 调用 `sdd-interview` 和 `sdd-domain`；`sdd-implement` 调用 `sdd-tdd` 和 `sdd-review`。每种方法只在一个 skill 里定义。
- **分发**：`link-skills.sh` 把 skill 软链到 `~/.claude/skills` 和 `~/.agents/skills`。遇到同名的真实目录会跳过，不会删除。
- **跨工具**：Claude Code 通过 `CLAUDE.md` 读到 `AGENTS.md`，其他工具直接读 `AGENTS.md`。工具不支持 skill 时，让 AI 直接读对应的 `SKILL.md` 并照着执行。
- 所有 skill 内容都保存在规则仓库里，不依赖 [mattpocock/skills](https://github.com/mattpocock/skills) 原仓库。

详见[规范正文](standard.md)第 9 节和[上手指南](getting-started.md)。

## 11. 推广计划

| 阶段 | 时长 | 内容 | 退出条件 |
|---|---|---|---|
| 0 准备 | 约 1 周 | 填写各项 TODO，架构师评审，接入试点服务 | v0.1 合并，试点人员完成上手 |
| 1 试点 | 2～3 周 | 1～2 人做 1 个 L2 需求加 1～2 个 L1 需求，每个需求完成后运行 `/sdd-retro` 复盘 | 修订出 v0.2 |
| 2 扩大 | 约 1 个月 | 一个小组的所有 L1、L2 需求 | 发布 v1.0 |
| 3 全团队 | — | 所有服务接入，MR 检查项作为合并条件 | — |

- **评估指标**：spec 评审发现的问题数、MR 被打回的次数、上线后因需求理解偏差导致的缺陷数、spec 与代码一致性抽查、开发者感受到的耗时。
- **8 个试点观察项**：L0 补写规格、评审人分工、手动切换状态、归档时限、跨工具调用 skill、参与服务的跨仓库操作、①②③ 能否在同一会话里完成、现状规格以主干为准。每项都写明了试点期的默认规则和要观察的内容。

详见[试点与推广计划](rollout-plan.md)。

## 12. 关键设计决策和理由

| 决策 | 理由 |
|---|---|
| 工作空间目录本身就是规则仓库 | 大家本来就这样打开 AI 工具；不用 submodule，不和服务仓库耦合 |
| spec 下沉到服务仓库（架构师要求） | spec 和代码在同一个 MR 里评审、合并，最不容易脱节 |
| 跨服务需求由主服务承载 | 弥补 spec 下沉后，整体信息没有存放位置的问题 |
| 自定义轻量规范，不用 Spec Kit 或 OpenSpec | 现成框架默认单仓库，而且会接管整个流程 |
| 按改动大小分档 | 避免小改动也走完整流程，导致团队抵触 |
| 阶段 skill 只能人工调用 | 不依赖 AI 自己判断是否触发 skill |
| 方法拆成独立 skill，统一加 `sdd-` 前缀 | 每种方法只有一个信源，可以单独使用，也避免和个人已安装的 skill 重名 |
| 取消"实现中"状态 | 避免在参与服务里修改主服务仓库的文件 |
| 现状规格以主干为准 | 和"随代码一起合并"的机制天然一致 |
| 存量文档不迁移 | 降低接入门槛，改到哪块补哪块 |
