# 团队 SDD 规范

- 版本：v0.1（试点版）
- 适用范围：本团队所有 Spring Boot 微服务的需求开发，不论是否使用 AI 编码工具
- 修改方式：本规范的任何修改都在规则仓库提 MR，经架构师评审后合并

## 1. 目标

SDD 要解决三个问题：

1. **需求理解偏差**：写代码之前，把歧义消灭在 spec 里，而不是在评审或上线后才发现。
2. **AI 输出不可控**：AI 按经过评审的 spec 和小任务实现，评审时有明确的对照标准。
3. **决策丢失**：需求、设计和关键决策留在仓库里，换人、换会话都能接上。

为此需要遵守三条原则：

- **先对齐，再动手。**
- **spec 是事实来源**：实现必须偏离 spec 时，先改 spec。
- **流程按改动大小分档**：小改动不走重流程。

## 2. 术语

| 术语 | 含义 |
|---|---|
| 规则仓库 | 本仓库，同时也是 AI 工作空间根目录，只放规则，不放真实需求的 spec（`docs/example/` 只用于演示） |
| 变更 spec | 描述"这次要改什么"的文档：`spec.md`、`design.md`、`tasks.md` |
| 现状规格 | 描述"系统现在是什么样"的文档，放在服务的 `docs/specs/` |
| 主服务 | 跨服务需求中承载完整 spec 和 design 的服务，通常是需求发起方或核心服务 |
| 参与服务 | 跨服务需求中，主服务以外涉及的服务 |
| 测试接缝 | 验证行为时所站的公共边界，例如 HTTP 接口、对外的 Service 接口、MQ 消费入口 |
| 垂直切片 | 贯穿所需各层、交付一段完整可验证行为的任务，与"按层拆分"相对 |
| 两轴审查 | 从 Standards（是否符合编码规范）和 Spec（是否忠实实现 spec）两个方向分别审查代码 |
| ADR | 架构决策记录，只记录难以撤销、经过取舍的决策 |

## 3. 文档放在哪

决策记录见 [ADR-0001](adr/0001-spec-in-service-repos.md)。

### 3.1 规则仓库（本仓库）

| 路径 | 内容 |
|---|---|
| `AGENTS.md` | 服务地图、分档、AI 工作方式（AI 每次会话都会读） |
| `GLOSSARY-MAP.md` | 各服务术语表的索引 |
| `docs/adr/` | 跨服务决策 |
| `docs/coding-standards.md` | 团队编码规范 |
| `skills/` | AI 执行各阶段的步骤和模板 |
| `templates/service/` | 服务仓库要用的模板 |

### 3.2 服务仓库

```
<服务>/
├── AGENTS.md / CLAUDE.md      本服务的约定（CLAUDE.md 只引用 AGENTS.md）
├── GLOSSARY.md                本服务的领域术语（需要时创建）
├── .gitlab/merge_request_templates/Default.md
└── docs/
    ├── specs/                 现状规格：README.md 索引 + 每个业务能力一个文件
    ├── adr/                   本服务内部的决策（需要时创建）
    └── changes/
        ├── <需求单号>-<英文短描述>/   进行中需求的变更 spec
        └── archive/<年份>/           已上线或已中止的变更 spec
```

命名、状态流转、职责、现状规格的更新义务、归档和存量文档的处理，见[服务仓库 spec 管理规范](spec-management.md)。

### 3.3 跨服务需求

- 主服务放完整的 `spec.md`、`design.md`，以及本服务的 `tasks.md`。
- 每个参与服务只放本服务的 `tasks.md`，开头用 `<主服务名>:<需求目录名>` 引用主服务的 spec。
- 主服务由 AI 在需求拷问阶段建议，开发者确认。

## 4. 分档

| 档位 | 适用场景 | 需要的文档 |
|---|---|---|
| L0 | bug 修复、小调整、配置变更 | 不需要 spec；commit 写清原因，补测试。疑难 bug 用 `sdd-diagnose` 排查 |
| L1 | 单个服务内的新功能或行为变化 | `spec.md`（一次会话做不完时加 `tasks.md`） |
| L2 | 跨服务需求、接口变更、表结构变更 | 主服务：`spec.md` + `design.md` + `tasks.md`；参与服务：`tasks.md` |

拿不准时按高一档处理。

## 5. 流程

```
L1/L2:  ① 需求拷问 ─► ② 写 spec ─► ③ 拆任务(L2) ─► ④ Draft MR 评审 ─► ⑤ 实现(每任务一次) ─► ⑥ MR 合并 ─► ⑦ 归档
        └────────── 同一个会话 ──────────┘                          └─ 每个任务一个新会话 ─┘
```

**上下文要求**：①②③ 在同一个 AI 会话里连续完成，这样 spec 和任务直接建立在原始讨论上，而不是建立在摘要上。⑤ 每个任务开一个新会话，只凭 spec 和任务描述工作。

| 阶段 | 命令 | 输入 | 产出 | 完成标准 |
|---|---|---|---|---|
| ① 需求拷问 | `/sdd-grill` | 需求单号和描述、现状规格、术语表 | 档位、主服务、共识；更新的术语表和 ADR | 决策树里没有未决问题，开发者确认共识 |
| ② 写 spec | `/sdd-spec` | 本会话的共识 | `spec.md`，L2 加 `design.md` | 测试接缝已确认；每条需求有编号且可测试；"待确认问题"为空 |
| ③ 拆任务 | `/sdd-tasks` | spec、design | 各服务的 `tasks.md` | 每条需求都被任务覆盖；开发者确认粒度和依赖 |
| ④ 评审 | 人工 | 各服务的 Draft MR | 评审意见、修订后的文档 | 第 6 节的 spec 评审检查项全部通过 |
| ⑤ 实现 | `/sdd-implement` | spec、本任务 | 代码、测试、更新后的现状规格 | 验收条件有测试且通过；两轴审查的问题已处理；已提交 |
| ⑥ 合并 | 人工 | MR | 合并到主干 | 第 6 节的代码评审检查项全部通过 |
| ⑦ 归档 | 人工 | 已上线的需求 | 状态改为"已上线"，变更目录移到 `docs/changes/archive/<年份>/` | 涉及的所有服务在上线后两周内完成归档 |

各阶段的具体步骤见 `skills/<命令名>/SKILL.md`，AI 按这些步骤执行，开发者也可以照着手动执行。

### 5.1 写 spec 的要求

- 需求用 EARS 句式，每条编号（R1、R2……），每条都能写成测试：`WHEN <条件>，THE SYSTEM SHALL <行为>`。
- "不做"一节必须有内容，没有就写"无"。
- 写明测试接缝：优先已有接缝，越高越好，越少越好。
- 用业务语言写，不写具体文件路径和代码片段。表结构、状态机、接口字段这类用代码表达更准确的决策可以摘录关键部分。
- 接口字段明细以接口文档平台为准，`design.md` 只写变更要点和兼容性。

### 5.2 拆任务的要求

- 每个任务是一条垂直切片，一次会话能做完。
- 预重构任务排在最前。
- 任务编号在整个需求内统一，阻塞依赖可以跨服务，并且和上线顺序一致。

### 5.3 实现的要求

- 测试先行：在确认过的接缝上，一次写一个失败的测试，再写刚好让它通过的代码。
- 测试通过公共接口验证行为；只 mock 服务边界之外的依赖。
- 实现范围以 spec 和任务为准；必须偏离时，先改 spec。
- 业务行为变化时，在同一个 MR 里更新对应能力已有的现状规格，并追加变更记录。这条对所有档位都适用，包括 L0；L0 改到的能力还没有现状规格时，试点期不强制补写，在 MR 里注明即可。接口变化时，同步到接口文档平台。

## 6. 评审

### 6.1 spec 评审（写代码之前）

在 feature 分支上先只提交文档，开 Draft MR。主服务的 MR 评审 spec、design、tasks，参与服务的 MR 评审各自的 tasks。检查项：

- [ ] "不做"清单明确
- [ ] 每条需求都能写成测试
- [ ] 测试接缝合理
- [ ] 待确认问题已清空
- [ ] （L2）服务影响矩阵完整，上线顺序和回滚方案可行
- [ ] （L2）任务依赖和上线顺序一致

主服务和所有参与服务的 Draft MR 都通过评审后，需求负责人把 spec 状态改为"已确认"，然后在同一个分支上继续写代码，spec 和代码最终在同一个 MR 里合并。

### 6.2 两轴审查（提 MR 之前）

每个任务完成后，由 AI 运行 `sdd-review`（`/sdd-implement` 会自动调用）：

- **Standards**：对照 `docs/coding-standards.md`、服务 `AGENTS.md` 里的编码约定，以及一组代码坏味道基线
- **Spec**：漏做的需求、范围蔓延、实现错误、现状规格没有同步

两个方向分开报告。审查发现的问题，要么修复，要么在 MR 里说明不修复的理由。

### 6.3 代码评审（合并之前）

reviewer 对照 spec 和 MR 模板里的自查项评审。重点看两轴审查没有覆盖的部分：业务正确性、上线风险。

## 7. 术语表与 ADR

- **术语表**：每个服务一份 `GLOSSARY.md`，一个概念只保留一个用词。需求拷问时发现术语冲突，当场确定并写入。格式和规则见 `skills/sdd-domain/SKILL.md`。
- **ADR**：同时满足"难以撤销""没有上下文会让人意外""确实经过取舍"三个条件才写，一段话即可。跨服务决策放规则仓库的 `docs/adr/`，服务内部决策放服务的 `docs/adr/`。
- 写 spec 或代码时与已有 ADR 冲突，必须明确指出，不能悄悄推翻。

## 8. Git 与 MR 约定

- 分支：`feature/<需求单号>-<英文短描述>`，修复用 `fix/<需求单号>-<英文短描述>`；L0 改动没有需求单号时，用 `fix/<英文短描述>`。同一个需求在各服务使用相同的分支名。
- commit：Conventional Commits，有需求单号时带上，例如 `feat(order): auto-cancel unpaid orders (REQ-12345)`。L1、L2 需求一定有需求单号。
- MR：使用服务仓库的 MR 模板（来自 `templates/service/merge_request.md`）。参与服务的 MR 描述里用 `<主服务名>:<需求目录名>` 引用主服务 spec。

## 9. AI 工具

- 规则统一写在 `AGENTS.md`。Claude Code 通过 `CLAUDE.md` 引用它；其他主流工具会直接读 `AGENTS.md`。
- skill 放在规则仓库的 `skills/`，由 `scripts/link-skills.sh` 软链到个人目录（`~/.claude/skills`、`~/.agents/skills`），`git pull` 即可更新。
- 所用工具不支持 skill，或不支持 skill 之间互相调用时，直接让 AI 读 `skills/<名称>/SKILL.md` 并按步骤执行，效果相同。
- AI 只负责起草和实现，评审结论由人做出。

skill 分三类：

| 类别 | skill | 怎么触发 | 用途 |
|---|---|---|---|
| 阶段 | `sdd-grill`、`sdd-spec`、`sdd-tasks`、`sdd-implement` | 开发者输入命令 | 编排第 5 节的四个 AI 阶段 |
| 方法 | `sdd-interview` | AI 自动调用，也可单独使用 | 多轮决策树提问（grilling） |
| 方法 | `sdd-domain` | 同上 | 维护术语表和 ADR |
| 方法 | `sdd-tdd` | 同上 | 测试先行开发 |
| 方法 | `sdd-review` | 同上 | 两轴代码审查 |
| 方法 | `sdd-diagnose` | 同上 | 疑难 bug 和性能退化的诊断 |
| 工具 | `sdd-questionnaire` | 开发者输入命令 | 把需要产品或业务方决定的问题整理成问卷 |
| 工具 | `sdd-handoff` | 开发者输入命令 | 把会话整理成交接文档，换工具或转交同事时使用 |
| 工具 | `sdd-retro` | 开发者输入命令 | 需求或会话结束后复盘，提出规则和模板的改进建议 |

阶段 skill 内部会调用方法 skill：`sdd-grill` 调用 `sdd-interview` 和 `sdd-domain`，`sdd-implement` 调用 `sdd-tdd` 和 `sdd-review`。每种方法只在一个 skill 里定义。
