# 团队 SDD 规范

- 版本：v0.4（试点版）
- 定位：集团《SDD开发规范》《SDD分级评估标准》《SDD模板》（v1.0，2026-10）的**单位级扩展与落地实施细则**。集团统一规范为强制底线，本规范只做两件事：把集团条款落成本团队的具体做法；在不删减、不弱化集团强制内容的前提下，补充本团队特有的扩展（见第 3.3 节）。
- 执行载体：接入研发云的服务仓由研发云 SDD 数字员工按 G0–G5 全流程执行（第 5 章）；数字员工包定义见本仓库 `docs/codefree/`。
- 适用范围：本团队所有 Spring Boot 微服务的需求开发，不论是否使用 AI 编码工具
- 修改方式：本规范的任何修改都在规则仓库提 MR，经架构师评审后合并

## 1. 目标

SDD 要解决三个问题：

1. **需求理解偏差**：写代码之前，把歧义消灭在 spec 里，而不是在评审或上线后才发现。
2. **AI 输出不可控**：AI 按经过评审的 spec 和小任务实现，评审时有明确的对照标准。
3. **决策丢失**：需求、设计和关键决策留在仓库里，换人、换会话都能接上。

为此需要遵守三条原则：

- **先对齐，再动手。**
- **spec 是事实来源**：实现必须偏离 spec 时，先改 spec。
- **流程按改动大小分档**：小改动不走重流程。

## 2. 术语

| 术语 | 含义 |
|---|---|
| 工作空间 | 放置规则仓库、治理仓和所有服务仓库的目录，AI 工具在这里打开；本身不纳入版本控制 |
| 规则仓库 | 本仓库，目录名 `sdd-standard/`；只放规则，不放真实需求的 spec（`docs/example/` 只用于演示） |
| 治理仓 | 目录名 `sdd-governance/`，承载项目级追溯工件的仓库：`prd-index.md`、主 spec、跨服务契约、跨服务需求的全局 spec 与 design（见第 4.3 节） |
| 服务仓库 | 各微服务的 git 仓库，承载本服务的现状规格、变更 spec 和代码 |
| 域 | Spec 编号的命名空间，一个服务一个域，取服务名去 `service` 后缀的大写（`order-service` → `ORDER`），登记在治理仓 `domains.yaml` |
| Spec ID | 现状规格的标识，格式 `SPEC-<域>-<NNN>`（三位序号，如 `SPEC-ORDER-001`），同一 Spec 终身不变，新需求沿用 |
| FR | 需求条目编号 `FR-xxx`，在一份现状规格内唯一；用 EARS 句式写成可验证的断言。本团队的 FR 同时充当集团规范里的 AC，测试用例以 `[FR-xxx]` 标注关联 |
| FEAT | 需求点编号 `FEAT-xxx`，项目级唯一，在 `/sdd-grill` 阶段分配，登记进治理仓 `prd-index.md`；一个需求单可以拆出多个 FEAT |
| prd-index | 需求追溯索引，治理仓的 `prd-index.md`；PRD 权威源模式为 `source: workitem`（需求系统），仓内不存 PRD 正文 |
| 变更 spec | 描述"这次要改什么"的提案文档：`spec.md`、`design.md`、`tasks.md`；评审通过后落进现状规格，归档后只是历史记录。平台仓不设独立提案文件，变更由 item、spec.md 的 diff 和 gate 报告承载（见第 5 章） |
| 现状规格 | 描述"系统现在是什么样"的文档，即集团规范里的"模块 Spec"，带 Spec ID 和 FR 编号，原地演进；平台仓位于 `docs/specs/SPEC-<域>-<NNN>/spec.md` |
| item | 平台状态机里的独立任务身份（UUID），一个需求或迭代一个 item，登记在服务仓 `docs/sdd-state.yaml`；同一 Spec 的新需求沿用 Spec ID 新建 item |
| gate 报告 | 平台每个阶段的逐项检查证据，位于 `docs/specs/<Spec ID>/items/<item_id>/reports/gateN-report.md` |
| 平台 agent | 研发云 SDD 数字员工：主 Agent + 阶段 skills + 本地 Git hooks + 研发云 MCP，按 `sdd-sop.yaml` 编排 G0–G5，包定义见本仓库 `docs/codefree/` |
| 目标版本 | 需求计划进入的版本，例如 `6.11.1`；对应的开发分支为 `develop-v<目标版本>` |
| 需求负责人 | 负责一个需求在所有涉及服务里的 spec、推进状态和归档的开发者，通常是需求发起方 |
| 测试接缝 | 验证行为时所站的公共边界，例如 HTTP 接口、对外的 Service 接口、MQ 消费入口 |
| 测试基座 | 服务的测试能否运行：全量（全量测试能跑通）、部分（能单独运行测试类）、无（没有可运行的测试） |
| 降级验证 | 服务没有可用的测试基座时，用可重复执行的脚本代替自动化测试验证行为；必须在 spec 里事先声明。对应集团"手工 AC + 核销载体"机制 |
| 垂直切片 | 贯穿所需各层、交付一段完整可验证行为的任务，与"按层拆分"相对 |
| 两轴自审 | AI 从 Standards（是否符合编码规范）和 Spec（是否忠实实现 spec）两个方向分别审查代码 |
| ADR | 架构决策记录，只记录难以撤销、经过取舍的决策 |

## 3. 与集团规范的关系

### 3.1 定位与优先级

集团三份文档是本规范的上位规范。两者冲突时，以集团规范为准，并按规则仓库 MR 修订本规范。本规范引用集团条款时写明出处（如《SDD开发规范》§2.4）。

### 3.2 分级体系语境

集团规范里有四套 L 编号，含义互不相同，引用时必须带语境（《SDD开发规范》§1.2）：

| 分级体系 | 取值 | 本团队怎么用 |
|---|---|---|
| 变更分级 | L1 微调 / L2 轻量 / L3 增量 / L4 重大 | 日常分档用，见第 6 节 |
| SDD 执行分级 | SDD-L2 基础 / SDD-L3 进阶 | 本团队目标为 SDD-L2；定级评估由集团平台承载，本规范为其准备证据 |
| 范式成熟度 | L0～L4 | 归集团管理，本规范不使用这套编号 |
| 智改产品分级 | 智改-L1～L4 | 按产品形态判定，产品含 AI 功能模块时启用对应的 Spec 扩展章节（《SDD模板》第 5～7 章） |

### 3.3 单位级扩展清单

以下是本规范在集团框架之上登记的单位级扩展，依据《SDD模板》§1.4"各业务单元可扩展本单位差异化内容"：

1. **测试基座三级完成标准与降级验证**：集团手工 AC 核销机制在本团队的实例化，核销载体为 Spec 目录 `verify/` 下的可重复执行脚本。
2. **现状规格按业务能力组织、存量渐进补写**：作为集团模块 Spec 的冷启动策略，第一次改到某能力时补写。
3. **FR 与 AC 合一**：FR 条目用 EARS 单句断言，一条 FR 即一条 AC，测试用例以 `[FR-xxx]` 标注，不另设 `AC-xxx-y` 编号。
4. **任务编号需求内统一**（T1、T2……）：集团格式为 `T-<域>-xxx`，在平台 commit trailer 校验上线时切换。
5. **提案形态双轨**：平台仓的变更由 item、spec.md 的 diff 和 gate 报告承载，`docs/changes/` 退役；未接入平台的仓保留变更 spec 目录（`docs/changes/<需求目录>/`）。两种形态都满足"行为规则的唯一权威在现状规格"（见第 5 章）。
6. **AI 会话编排**：需求澄清与写 spec 同一会话、每任务一个新会话、交接文档（第 6 节）。
7. **术语表与 ADR 治理**（第 8 节）。
8. **目标版本分支模型**：`develop-v<目标版本>`、`release-v<目标版本>` 并存的版本列车。
9. **sdd-* skills**：各阶段的 AI 执行步骤（第 11 节）。

### 3.4 过渡通道

平台能力未就绪期间，按集团《SDD分级评估标准》§5.5 登记的过渡通道执行：

- **commit trailer**：集团要求代码提交带 `Spec-Id:`/`Task-Id:` trailer（TR-05）。**平台仓不适用本通道**——hooks 已强制 trailer（见 5.3）；仅未接入平台的仓过渡期以 MR 描述里的 Spec/Task 清单承载同等信息（MR 模板已内置）。
- **跨服务批次**：集团要求跨仓行为变更批次内全部 MR 通过后才准合入（G4-10），过渡期以 design 里声明的上线顺序做人工批次核对：有依赖关系的服务，后上线方的 MR 合并前确认先上线方已合并。
- **AGENTS.md 与门禁**：Git hooks、CI 门禁在平台方案确定后接入，`check-spec.sh` 先行承担本地校验。

## 4. 文档放在哪

决策记录见 [ADR-0001](adr/0001-spec-in-service-repos.md)。

### 4.1 工作空间布局

```
<工作空间>/                不纳入版本控制
├── AGENTS.md / CLAUDE.md  指向规则仓库的指针文件（bootstrap.sh 生成）
├── sdd-standard/          规则仓库（本仓库）
├── sdd-governance/        治理仓（项目级追溯工件）
├── order-service/         服务仓库，各自独立，内有 sdd/ 只读引用治理仓
├── inventory-service/
└── ...                    工作空间里的其他项目不受本规范约束
```

规则仓库、治理仓与服务仓库并列。各服务通过父 POM 的相对路径互相引用时，这种布局不影响构建。

### 4.2 规则仓库（本仓库）

| 路径 | 内容 |
|---|---|
| `AGENTS.md` | 服务地图、版本分支、分档、AI 工作方式（AI 每次会话都会读） |
| `GLOSSARY-MAP.md` | 各服务术语表的索引 |
| `docs/adr/` | 跨服务决策 |
| `docs/coding-standards.md` | 团队编码规范 |
| `skills/` | AI 执行各阶段的步骤和模板 |
| `templates/` | 服务仓库、治理仓和工作空间要用的模板 |
| `scripts/` | 初始化工作空间、链接 skill、提 MR 前的校验 |

规则仓库是团队的规范库，对应集团分层继承里的"通用模板"层；服务 AGENTS.md 只写本服务特有规则，不复制本仓库的通用内容。

### 4.3 治理仓（sdd-governance）

一个研发云项目一个治理仓。本团队所有服务同属一个项目，共用一个治理仓：

```
sdd-governance/
├── AGENTS.md             三章结构（版本信息/核心原则/AI 安全约束）
├── repos.yaml            仓清单：各服务仓的 git 地址、域、豁免理由
├── domains.yaml          域清单：域 → 归属仓
├── prd-index.md          需求追溯索引（source: workitem）
├── spec.md               主 spec：FEAT 映射表 + 各服务能力索引（不写功能需求正文）
├── spec-contract-<主题>.md  跨服务契约（接口契约、跨服务业务规则）
└── changes/<需求目录>/   跨服务需求的全局 spec.md 和 design.md
```

治理仓禁止存放业务代码和服务的模块 Spec。各服务仓以 `sdd/` 子目录（git submodule）只读引用治理仓：只读、版本锁定、修改必须回治理仓走 MR。初始化模板见 `templates/governance/`。

### 4.4 服务仓库

接入平台的服务仓（全部服务的目标形态）：

```
<服务>/
├── AGENTS.md / CLAUDE.md      本服务的约定（三章结构；平台 init 生成或人工维护）
├── GLOSSARY.md                本服务的领域术语（核心域服务必须有，其他按需）
├── sdd/                       治理仓的只读引用（git submodule）
└── docs/
    ├── prd-index.md           需求追溯索引（source: workitem，平台维护）
    ├── sdd-state.yaml         平台状态机（数字员工脚本独占写，人工不编辑）
    └── specs/
        ├── README.md          人读能力索引（单位级扩展，平台不消费）
        └── SPEC-ORDER-001/    一个 Spec 一个目录，原地演进
            ├── spec.md        现状规格：业务规则（FR）+ 当前 item 范围 + 变更历史
            ├── design.md      设计（G2 产出）
            ├── tasks.md       任务清单（G3 产出）
            ├── adrs/、api/、ui/
            ├── verify/        降级验证脚本（单位级扩展，手工 AC 核销载体）
            └── items/<item_id>/reports/   gate0～5 报告、单测报告
```

尚未接入平台的仓维持旧布局（`docs/changes/<需求目录>/` + 扁平的 `docs/specs/<能力>.md`），按第 5.6 节迁移后切换。命名、状态流转、职责、现状规格的更新义务、历史与追溯，见[服务仓库 spec 管理规范](spec-management.md)。

### 4.5 跨服务需求

- 治理仓 `changes/<需求目录>/` 放全局 `spec.md`（背景、FEAT 分配、范围、不做、跨服务契约变更）和 `design.md`（服务影响矩阵、接口变更要点、上线顺序与回滚）。
- 每个涉及的服务仓 `docs/changes/<需求目录>/` 放本服务的 `spec.md`（FR 条目）和 `tasks.md`，经 `sdd/` 引用治理仓的全局 spec。平台仓不建需求目录：本服务部分由平台 G1/G3 写进 `docs/specs/SPEC-xxx/`（见第 5 章）。
- 需求负责人由 `/sdd-grill` 建议、开发者确认，通常是需求发起方；负责所有涉及服务的 spec 推进和归档，不再有"主服务承载完整 spec"的角色。
- 跨服务的接口契约变更落在治理仓 `spec-contract-<主题>.md`，同 MR 更新。

### 4.6 ID 与追溯

| 对象 | 编号 | 唯一性范围 | 登记位置 |
|---|---|---|---|
| 需求点 | `FEAT-xxx` | 项目内唯一 | 治理仓 `prd-index.md` |
| 现状规格 | `SPEC-<域>-<NNN>` | 项目内唯一 | 目录名 + 文件头部元数据 |
| 需求条目 | `FR-xxx` | 一份现状规格内唯一 | 现状规格正文；跨服务引用写全限定 `[SPEC-ORDER-001/FR-003]` |
| 任务 | `T1、T2……` | 需求内统一 | 各服务 `tasks.md` |
| 需求单号 | 纯数字 | 需求系统内唯一 | 目录名、分支名、commit、MR |

`/sdd-grill` 负责建议 FEAT 编号和 prd-index 条目，`/sdd-spec` 负责分配 FR 编号和 Spec ID，`/sdd-tasks` 负责任务编号。FR 新增、修改、删除都在变更 spec 里引用编号；评审通过后同 MR 落进现状规格和治理仓主 spec 的 FEAT 映射表。

## 5. 平台执行载体：研发云 SDD 数字员工

### 5.1 定位与适用范围

研发云 SDD 数字员工是集团规范的**平台侧参考实现**：主 Agent 编排阶段 skills，按 `sdd-sop.yaml` 执行 G0–G5 六阶段，逐项产出 gate 报告，配本地 Git hooks、`sdd-state.yaml` 状态机和研发云 MCP（安全扫描、代码中心 MR）。包定义（`sdd-sop.yaml`、`sdd-state-template.yaml`、`sdd-dev-engineer.md`）保存在本仓库 `docs/codefree/`。

**适用范围（已拍板：全面切换）**：所有接入研发云的服务仓，L2～L4 需求全量由平台 agent 执行，不再走第 7～8 章的人工流程；L1 微调不走平台流程，直接修改 + 回归测试 + MR 评审。跨服务编排（治理仓、全局 spec、批次）不归平台 agent，仍由 sdd-* skills 承担（见 5.5）。

### 5.2 阶段映射

| 本规范流程（第 6～8 章） | 平台阶段 | 平台产物与门禁 |
|---|---|---|
| ① 需求澄清（sdd-grill）+ init | G0 需求分析 | prd-index 登记、G0-01～08 报告、需求侧人工评审 |
| ② 写 spec（sdd-spec） | G1 Spec 准入 | `SPEC-xxx/spec.md`、G1-01～22 报告、Spec MR 人工评审 |
| design.md（L4/跨服务） | G2 设计审查 | design.md、ADR、OpenAPI、G2-01～12 报告、阶段 MR |
| ③ 拆任务（sdd-tasks） | G3 任务审查 | tasks.md、G3-01～06 报告、阶段 MR |
| ⑤ 实现（sdd-implement） | G4 编码实现 | 每 Task 一个 commit、单测报告、G4-01～10、Code MR |
| ⑥ 合并 + 验证 | G5 验收验证 | SQSC 安全扫描、G5-01～24 报告、人工终验后 finalize |

每阶段一个 MR、人工评审通过才进下一阶段；不使用我们的闸口合并轻量通道（平台 SOP 固定六阶段）。L2 轻量需求同样走全六阶段，这是全面切换接受的流程成本。

### 5.3 关键约定

- **提案要素落位**：我们提案里的"不做清单、待确认问题、降级验证声明"在平台模板没有对应章节，登记在 `SPEC-xxx/spec.md` 的"当前 item"段（评审通过后转入变更历史）；降级验证脚本放 `SPEC-xxx/verify/`（单位级扩展）。
- **commit trailer 立即启用**：平台 hooks 强制 `%<工作项ID> <type>(<scope>):` 首行 + 代码带 `Spec-Id:`+`Task-Id:`、文档只带 `Spec-Id:`，即集团 T-01 全量落地；第 10 章的 TR-05 过渡（MR 级关联）**不适用于平台仓**。状态提交另带 `SDD-Item-Id:`、`SDD-Node-Id:`。
- **分支**：源分支用平台默认 `sdd/<工作项ID><用户ID>`；`item.git.target_branch` 登记为我们的 `develop-v<目标版本>`，版本列车不变。
- **MR**：由平台 agent 按固定格式创建并附完整链接，人工评审在研发云代码中心进行；agent 不自动批准、合并。
- **本地校验**：`check-spec.sh` 在平台仓自动切换平台模式（见脚本内说明），门禁以平台 hooks 和 gate 报告为准。

### 5.4 人工职责变化

阶段推进由人工触发（"继续"不等于批准）；每阶段 MR 的人工评审、G0 需求确认、G5 终验、返工裁决仍由人签署。需求负责人仍负责治理仓登记（FEAT、prd-index、全局 spec）与跨服务协调；状态推进、报告生成、提交与 MR 操作由 agent 执行，人核对。

### 5.5 与治理仓的关系

平台 agent 是**单仓视角**，不感知治理仓。跨服务需求保持双层：治理仓的全局 spec/design、FEAT 分配、契约变更由 sdd-* skills 编排（人工触发）；各服务仓内部由平台 agent 执行。服务仓经 `sdd/` submodule 只读消费治理仓，agent 在仓内的提交不得触碰 `sdd/` 目录。

### 5.6 存量迁移（每仓一次）

1. 进行中的 `docs/changes/<需求目录>/` 走完旧流程，不迁移，自然清零。
2. `docs/specs/<能力>.md` 重组为 `docs/specs/SPEC-<域>-<NNN>/spec.md`：`git mv` 建目录，头部 Spec ID 提升为目录名，序号补足三位；能力索引同步。
3. `docs/api/` 的 OpenAPI 移入对应 Spec 的 `api/`；`docs/adr/` 移入相关 Spec 的 `adrs/`。
4. 在研发云接入数字员工包，由 init 生成 `docs/sdd-state.yaml`、安装 hooks、登记项目绑定；此后新需求一律走平台流程。

## 6. 分档

分档采用集团变更分级（《SDD开发规范》§8.1、§8.9），从高定级：任一维度命中更高档位就按更高档执行，拿不准时按高一档处理。

| 档位 | 场景 | 需要的文档 |
|---|---|---|
| L1 微调 | bug 修复（代码不符合 spec，spec 本身正确）、文案与格式调整、不改业务行为的配置调整、纯重构、文档纠错 | 不写变更 spec；修复类必须补回归测试 |
| L2 轻量 | 单服务内的纯新增小需求：新增 FR≤2 且 AC≤5、预估 ≤2 人日、不改既有 FR/AC、不新增对外接口 | `spec.md` + `tasks.md`（都可从简）；接口兼容性写进"非功能要求" |
| L3 增量 | 纯新增超出 L2 的量化条件：新增对外接口或可选字段（不影响既有调用方）、新增 FR≥3 或 AC>5、跨服务的纯新增 | 单服务：`spec.md` + `tasks.md`；跨服务：治理仓全局 spec + design + 各服务 spec + tasks |
| L4 重大 | 修改既有行为语义（校验规则、状态流转、返回值语义）、不兼容接口变更（改字段含义、删接口、改必填）、表结构变更（改字段类型、删字段、改主键/索引）、跨服务既有契约变更、有上线顺序依赖的跨服务改动 | 同 L3，`design.md` 必备；跨服务走治理仓流程和批次合入纪律 |

**bug 修复的定档**：代码违反 spec、spec 正确的（集团 A 类归因）走 L1；修复中发现 spec 缺失或错误的（B/C 类归因），先停下改 spec（按本表重新定档），再修代码，禁止按 L1 直接改完。

**配置变更的定档**：不改变对外行为的配置调整走 L1；改变行为的（改开关默认值等）按 L2～L4 判定，开关控制的规则要写进现状规格并注明开关名。

**与旧档位的对应**：

| 旧档位 | 新档位 |
|---|---|
| 旧 L0 | L1（多数）；改变业务行为的配置变更按 L2～L4 判定 |
| 旧 L1 | L2（满足量化条件）或 L3（含向后兼容的接口新增） |
| 旧 L2 | L4（多数）；跨服务的纯新增走 L3 |

**执行载体注记**：接入平台的服务仓，L2～L4 由数字员工按 G0–G5 执行（第 5 章），本节只决定"要写什么文档、算什么变更"，与执行载体无关；未接入仓按第 7～8 章的人工流程走。

## 7. 流程

```
L2/L3/L4:  ① 需求澄清 ─► ② 写 spec ─► ③ 拆任务 ─► ④ Draft MR 评审 ─► ⑤ 实现(每任务一次) ─► ⑥ MR 合并 ─► ⑦ 归档
           └──── 同一个会话 ────┘                                     └─ 每个任务一个新会话 ─┘
L1:        直接修改，补回归测试 ─► MR 评审 ─► 合并

平台仓:    G0 需求分析 ─► G1 Spec 准入 ─► G2 设计 ─► G3 任务 ─► G4 编码 ─► G5 验收（每阶段一个 MR，人工评审）
           由数字员工执行，阶段映射见第 5.2 节
```

**上下文要求**：

- ①② 必须在同一个 AI 会话里连续完成，这样 spec 直接建立在原始讨论上，而不是建立在摘要上。
- ③ 优先在同一个会话里完成。需求涉及的服务多、会话过长时，可以先用 `/sdd-handoff` 生成交接文档，再开新会话拆任务。
- ⑤ 每个任务开一个新会话，只凭 spec 和任务描述工作。L2 需求任务少时，允许以整个 spec 为一次实现的范围。

| 阶段 | 命令 | 输入 | 产出 | 完成标准 |
|---|---|---|---|---|
| ① 需求澄清 | `/sdd-grill` | 需求单号和描述、目标版本、现状规格、术语表 | 档位、FEAT 编号、涉及服务、feature 分支、prd-index 条目、共识 | 决策树里没有未决问题，开发者确认共识 |
| ② 写 spec | `/sdd-spec` | 本会话的共识 | `spec.md`（FR 编号）；L3 跨服务和 L4 加治理仓全局 spec 与 `design.md` | 测试接缝和验证方式已确认；每条需求有 FR 编号且可验证；"待确认问题"为空 |
| ③ 拆任务 | `/sdd-tasks` | spec、design | 各服务的 `tasks.md` | 每条需求都被任务覆盖；开发者确认粒度和依赖 |
| ④ 评审 | 人工 | 各仓库的 Draft MR | 评审意见、修订后的文档；状态改为"已确认" | 第 8.1 节的检查项全部通过 |
| ⑤ 实现 | `/sdd-implement` | spec、本任务 | 代码、测试或降级验证脚本、更新后的现状规格 | 第 7.3 节的完成标准 |
| ⑥ 合并 | 人工 | MR | 合并到 `develop-v<目标版本>`；跨服务按上线顺序做批次核对 | 第 8.3、8.4 节通过 |
| ⑦ 归档 | 人工 | 已发布的需求 | 状态改为"已上线"，变更目录移到 `docs/changes/archive/<年份>/`（治理仓同理） | 目标版本发布后，在下一个版本的开发周期内完成 |

各阶段的具体步骤见 `skills/<命令名>/SKILL.md`，AI 按这些步骤执行，开发者也可以照着手动执行。

### 7.1 写 spec 的要求

- 写明目标版本。
- 需求条目用 EARS 句式、按第 4.6 节分配 FR 编号，每条都能验证：`WHEN <条件>，THE SYSTEM SHALL <行为>`。修改既有条目的引用原编号，不改语义。
- "不做"一节必须有内容，没有就写"无"。
- 写明测试接缝和每个接缝的验证方式：自动化测试（自动），或降级验证（手工，核销载体为 `verify/` 脚本）。服务的测试基座为"无"时，必须在这里声明降级验证。
- 用业务语言写，不写具体文件路径和代码片段。表结构、状态机、接口字段这类用代码表达更准确的决策可以摘录关键部分。
- 涉及对外接口的新增或变更：MR 附 OpenAPI 片段并落进 `docs/api/`，接口文档平台从仓内同步展示；spec 和 design 只写变更要点和兼容性。第三方定义的接口以第三方文档为约束源，不要求 OpenAPI。

### 7.2 拆任务的要求

- 每个任务是一条垂直切片，一次会话能做完。
- 预重构任务排在最前。
- 任务编号在整个需求内统一，阻塞依赖可以跨服务，并且和 design 的上线顺序一致。

### 7.3 实现的要求

- 测试先行：在确认过的接缝上，一次写一个失败的测试，再写刚好让它通过的代码。只 mock 服务边界之外的依赖。测试代码以 `[FR-xxx]` 注解标注关联的条目。
- 服务没有可用测试基座时，按 spec 声明的降级方式验证：写可重复执行的验证脚本，先确认它能暴露问题，再实现。
- 实现范围以 spec 和任务为准；必须偏离时，先改 spec。
- 业务行为变化时，在同一个 MR 里更新对应能力已有的现状规格（FR 条目和变更记录），并同步治理仓主 spec 的 FEAT 映射表。这条对所有档位都适用，包括 L1；L1 改到的能力还没有现状规格时，试点期不强制补写，在 MR 里注明即可。接口变化时，同步 OpenAPI 文件和接口文档平台。

**完成标准**：

| 服务的测试基座 | 完成标准 |
|---|---|
| 全量 | 约定接缝上的测试通过，全量测试通过 |
| 部分 | 约定接缝上的测试通过，受影响模块编译通过 |
| 无 | spec 声明的降级验证通过，受影响模块编译通过 |

三种情况都要在 MR 里列出没有被验证覆盖的部分。

## 8. 评审

### 8.1 spec 评审（写代码之前）

在 feature 分支上先只提交文档，开 Draft MR。跨服务需求在治理仓和各服务仓分别开 MR：治理仓的 MR 评审全局 spec、design 和契约变更，服务仓的 MR 评审本服务的 spec 和 tasks。检查项：

- [ ] 目标版本明确
- [ ] "不做"清单明确
- [ ] 每条需求都有 FR 编号且能验证
- [ ] FEAT 已登记进 prd-index，FR 变化会同步 FEAT 映射表
- [ ] 测试接缝和验证方式合理；声明了降级验证的，理由成立
- [ ] 待确认问题已清空
- [ ] （L3 跨服务、L4）服务影响矩阵完整，各服务的目标分支明确，上线顺序和回滚方案可行
- [ ] （L3 跨服务、L4）任务依赖和上线顺序一致

治理仓和所有服务仓的 Draft MR 都通过评审后，需求负责人把 spec 状态改为"已确认"，然后在同一个分支上继续写代码，spec 和代码最终在同一个 MR 里合并。

### 8.2 两轴自审

每个任务完成后，由 AI 运行 `sdd-review`（`/sdd-implement` 会自动调用）：

- **Standards**：对照 `docs/coding-standards.md`、服务 `AGENTS.md` 里的编码约定，以及一组代码坏味道基线
- **Spec**：漏做的需求、范围蔓延、实现错误、现状规格没有同步、声明的验证方式没有落实

两个方向分开报告。审查发现的问题，要么修复，要么在 MR 里说明不修复的理由。

两轴自审是提交给人评审之前的第一遍过滤，**不构成合并条件**；合并与否由第 8.4 节的代码评审决定。

### 8.3 提 MR 前的校验

提 MR 前，在服务目录下运行 `../sdd-standard/scripts/check-spec.sh`。脚本检查：

- feature 分支对应的变更 spec 目录存在，状态取值合法；spec 还没"已确认"就出现代码改动时报错
- 代码有改动但现状规格没有变化时给出提醒（是否涉及业务行为由人判断）
- 现状规格文件都已登记到索引，文件和目录命名符合规则

报错必须处理后才能提交评审；提醒由 MR 作者判断，并在 MR 里说明。

### 8.4 代码评审（合并之前）

reviewer 对照 spec 和 MR 模板里的自查项评审。重点看两轴自审覆盖不了的部分：业务正确性、上线风险、没有被验证覆盖的部分是否可以接受。跨服务需求按 design 的上线顺序做批次核对：后上线方的 MR 合并前，确认先上线方的 MR 已合并。

## 9. 术语表与 ADR

- **术语表**：核心域服务必须维护 `GLOSSARY.md`，其他服务按需创建。核心域的范围由架构师确认，初步包括设备、家庭、分享、用户、外部集成相关的服务。一个概念只保留一个用词；需求澄清时发现术语冲突，当场确定并写入。格式和规则见 `skills/sdd-domain/SKILL.md`。
- **ADR**：同时满足"难以撤销""没有上下文会让人意外""确实经过取舍"三个条件才写，一段话即可。跨服务决策放规则仓库的 `docs/adr/`，服务内部决策放服务的 `docs/adr/`。
- 写 spec 或代码时与已有 ADR 冲突，必须明确指出，不能悄悄推翻。

## 10. Git 与 MR 约定

- **分支**：feature 分支从 `develop-v<目标版本>` 拉出，命名为 `feature/<需求单号>-<英文短描述>`，同一个需求在各服务使用相同的分支名；治理仓同样使用该分支名。平台仓的源分支用平台默认 `sdd/<工作项ID><用户ID>`，目标分支登记为 `develop-v<目标版本>`（见 5.3）。修复分支从需要修复的版本分支拉出，命名为 `fix/<需求单号>-<英文短描述>`，L1 没有需求单号时用 `fix/<英文短描述>`。
- **MR**：合并回拉出它的版本分支。使用服务仓库的 MR 模板（来自 `templates/service/merge_request.md`）；跨服务需求治理仓的 MR 用同一模板。MR 描述里的 Spec/Task 清单在平台 commit trailer 校验上线前，承载集团 TR-05 过渡通道要求的关联信息。
- **commit**：第一行统一为 `%<需求单号> <type>(<scope>): <说明>`，冒号用半角，说明可以用中文。type 从封闭词表取值：代码改动用 `feat`、`fix`、`perf`；只改文档（`docs/`、`*.md`、OpenAPI）用 `docs`；构建、CI、不改行为的重构用 `chore`、`style`、`build`、`ci`、`refactor`，并在说明里注明"无行为变更"。scope 填服务名或模块名。**平台仓由 hooks 强制补齐 trailer**：代码提交带 `Spec-Id:`+`Task-Id:`，文档提交只带 `Spec-Id:`（集团 T-01，不设过渡）；未接入平台的仓过渡期不要求 trailer，由 MR 模板的 Spec/Task 清单承载（TR-05）。

  ```
  %184945 feat(order): 车企通知与设备消息订阅增加Apollo开关并默认关闭
  %18978 docs(order): 补充订单超时取消的现状规格
  %17100 fix(auth): 调整鉴权
  ```

- **存量**：已有的 commit、分支和文档不做迁移，本节只约束新的需求。

## 11. 与既有体系的关系

SDD 规范只规定**需求文档层**（spec 写什么、放在哪、怎么评审）和质量关口，不替换团队已有的任务分档、工具链和 AI 工具配置。两者重叠时按下面的顺序处理：

1. **服务仓库自己的工程约定优先**：服务 `AGENTS.md`、构建配置、既有 skill 或 agent 规定的编码方式和工具用法，优先于本规范里的通用编码要求。
2. **需求文档相关的环节使用 `sdd-*` skill**：需求澄清、写 spec、拆任务、对照 spec 审查。其他环节沿用既有工具。
3. **已经使用 OpenSpec 的服务**：按[迁移指南](spec-management.md)第 8 节迁到 `docs/` 结构，迁移完成前按存量对应关系执行。
4. **既有任务分档**：和 L1～L4 的对应关系见下表。既有分档来自根 `AGENTS.md` 的工作流车道，按"文件数 → 模块数 → 风险"判定。

| 既有分档 | 判定依据 | 对应的 SDD 档位 | 说明 |
|---|---|---|---|
| 🟢 简单 | 不超过 3 个文件、单模块、无架构风险 | L1 或 L2 | bug、配置、格式调整按 L1；有行为变化的纯新增小需求按 L2 |
| 🟡 标准 | 3～10 个文件、可能有兼容性风险 | L2 或 L3 | 按第 6 节的量化条件拆：FR≤2 且 AC≤5 走 L2；新增接口、超出条件走 L3 |
| 🔴 专家团 | 超过 10 个文件，或跨模块，或架构决策，或外部集成 | L3 或 L4 | 按第 6 节判断：纯新增走 L3；不兼容变更、表结构、跨服务契约走 L4。专家团的领域审查结论并入第 8.1 节的 spec 评审，不另增一次评审环节 |

**两者判断不一致时，以第 6 节为准。** 既有分档决定"改动有多大、谁参与"，只影响评审角色；SDD 分档决定"要不要写 spec、写几份"，只影响文档和评审范围。

## 12. AI 工具

- 工作空间根目录的 `AGENTS.md` 和 `CLAUDE.md` 指向规则仓库的 `AGENTS.md`。Claude Code 通过 `CLAUDE.md` 读取，其他主流工具读 `AGENTS.md`。
- skill 放在规则仓库的 `skills/`，由 `scripts/link-skills.sh` 软链到个人目录（`~/.claude/skills`、`~/.agents/skills`），`git pull` 即可更新。
- 所用工具不支持 skill，或不支持 skill 之间互相调用时，直接让 AI 读 `skills/<名称>/SKILL.md` 并按步骤执行，效果相同。
- 工作空间里有代码索引或代码图工具的，AI 在探索代码时优先使用。
- AI 只负责起草和实现，评审结论由人做出。

skill 分三类：

| 类别 | skill | 怎么触发 | 用途 |
|---|---|---|---|
| 阶段 | `sdd-grill`、`sdd-spec`、`sdd-tasks`、`sdd-implement` | 开发者输入命令 | 编排第 7 节的四个 AI 阶段（未接入平台的仓；平台仓见第 5 章） |
| 方法 | `sdd-interview` | AI 自动调用，也可单独使用 | 多轮决策树提问 |
| 方法 | `sdd-domain` | 同上 | 维护术语表和 ADR |
| 方法 | `sdd-tdd` | 同上 | 测试先行开发，包括降级验证 |
| 方法 | `sdd-review` | 同上 | 两轴自审 |
| 方法 | `sdd-diagnose` | 同上 | 疑难 bug 和性能退化的诊断 |
| 工具 | `sdd-questionnaire` | 开发者输入命令 | 把需要产品或业务方决定的问题整理成问卷 |
| 工具 | `sdd-handoff` | 开发者输入命令 | 把会话整理成交接文档，换工具、换会话或转交同事时使用 |
| 工具 | `sdd-retro` | 开发者输入命令 | 需求或会话结束后复盘，提出规则和模板的改进建议 |

阶段 skill 内部会调用方法 skill：`sdd-grill` 调用 `sdd-interview` 和 `sdd-domain`，`sdd-implement` 调用 `sdd-tdd` 和 `sdd-review`。每种方法只在一个 skill 里定义。
