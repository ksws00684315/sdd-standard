# 团队 SDD 规范

- 版本：v0.2（试点版）
- 适用范围：本团队所有 Spring Boot 微服务的需求开发，不论是否使用 AI 编码工具
- 修改方式：本规范的任何修改都在规则仓库提 MR，经架构师评审后合并

## 1. 目标

SDD 要解决三个问题：

1. **需求理解偏差**：写代码之前，把歧义消灭在 spec 里，而不是在评审或上线后才发现。
2. **AI 输出不可控**：AI 按经过评审的 spec 和小任务实现，评审时有明确的对照标准。
3. **决策丢失**：需求、设计和关键决策留在仓库里，换人、换会话都能接上。

为此需要遵守三条原则：

- **先对齐，再动手。**
- **spec 是事实来源**：实现必须偏离 spec 时，先改 spec。
- **流程按改动大小分档**：小改动不走重流程。

## 2. 术语

| 术语 | 含义 |
|---|---|
| 工作空间 | 放置规则仓库和所有服务仓库的目录，AI 工具在这里打开；本身不纳入版本控制 |
| 规则仓库 | 本仓库，在工作空间里与各服务仓库并列，目录名为 `sdd-standard`；只放规则，不放真实需求的 spec（`docs/example/` 只用于演示） |
| 变更 spec | 描述"这次要改什么"的文档：`spec.md`、`design.md`、`tasks.md` |
| 现状规格 | 描述"系统现在是什么样"的文档，放在服务的 `docs/specs/`，描述它所在分支上的代码 |
| 目标版本 | 需求计划进入的版本，例如 `6.11.1`；对应的开发分支为 `develop-v<目标版本>` |
| 主服务 | 跨服务需求中承载完整 spec 和 design 的服务，通常是需求发起方或核心服务 |
| 参与服务 | 跨服务需求中，主服务以外涉及的服务 |
| 测试接缝 | 验证行为时所站的公共边界，例如 HTTP 接口、对外的 Service 接口、MQ 消费入口 |
| 测试基座 | 服务的测试能否运行：全量（全量测试能跑通）、部分（能单独运行测试类）、无（没有可运行的测试） |
| 降级验证 | 服务没有可用的测试基座时，用可重复执行的脚本代替自动化测试验证行为，必须在 spec 里事先声明 |
| 垂直切片 | 贯穿所需各层、交付一段完整可验证行为的任务，与"按层拆分"相对 |
| 两轴自审 | AI 从 Standards（是否符合编码规范）和 Spec（是否忠实实现 spec）两个方向分别审查代码 |
| ADR | 架构决策记录，只记录难以撤销、经过取舍的决策 |

## 3. 文档放在哪

决策记录见 [ADR-0001](adr/0001-spec-in-service-repos.md)。

### 3.1 工作空间布局

```
<工作空间>/                不纳入版本控制
├── AGENTS.md / CLAUDE.md  指向规则仓库的指针文件（bootstrap.sh 生成）
├── sdd-standard/          规则仓库
├── order-service/         服务仓库，各自独立
├── inventory-service/
└── ...                    工作空间里的其他项目不受本规范约束
```

规则仓库在工作空间里与服务仓库并列。各服务通过父 POM 的相对路径互相引用时，这种布局不影响构建。

### 3.2 规则仓库（本仓库）

| 路径 | 内容 |
|---|---|
| `AGENTS.md` | 服务地图、版本分支、分档、AI 工作方式（AI 每次会话都会读） |
| `GLOSSARY-MAP.md` | 各服务术语表的索引 |
| `docs/adr/` | 跨服务决策 |
| `docs/coding-standards.md` | 团队编码规范 |
| `skills/` | AI 执行各阶段的步骤和模板 |
| `templates/` | 服务仓库和工作空间要用的模板 |
| `scripts/` | 初始化工作空间、链接 skill、提 MR 前的校验 |

### 3.3 服务仓库

```
<服务>/
├── AGENTS.md / CLAUDE.md      本服务的约定（CLAUDE.md 只引用 AGENTS.md）
├── GLOSSARY.md                本服务的领域术语（核心域服务必须有，其他按需）
├── .gitlab/merge_request_templates/Default.md
└── docs/
    ├── specs/                 现状规格：README.md 索引 + 每个业务能力一个文件
    ├── adr/                   本服务内部的决策（需要时创建）
    └── changes/
        ├── <需求单号>-<英文短描述>/   进行中需求的变更 spec
        └── archive/<年份>/           已上线或已中止的变更 spec
```

已经使用 OpenSpec 的服务保留 `openspec/` 目录结构，对应关系见[服务仓库 spec 管理规范](spec-management.md)第 8 节。命名、状态流转、职责、现状规格的更新义务、归档和存量文档的处理，也都在这份管理规范里。

### 3.4 跨服务需求

- 主服务放完整的 `spec.md`、`design.md`，以及本服务的 `tasks.md`。
- 每个参与服务只放本服务的 `tasks.md`，开头用 `<主服务名>:<需求目录名>` 引用主服务的 spec。
- 主服务由 AI 在需求澄清阶段建议，开发者确认。

## 4. 分档

| 档位 | 适用场景 | 需要的文档 |
|---|---|---|
| L0 | bug 修复、小调整、配置变更 | 不需要 spec；commit 写清原因，补测试。疑难 bug 用 `sdd-diagnose` 排查 |
| L1 | 单个服务内的新功能或行为变化，包括向后兼容的接口新增（新增可选字段、新增接口） | `spec.md`（一次会话做不完时加 `tasks.md`）；有接口新增时，在"非功能要求"里写明兼容性 |
| L2 | 跨服务需求、不兼容的接口变更（字段语义变化、删除或改为必填）、表结构变更、有上线顺序依赖的改动 | 主服务：`spec.md` + `design.md` + `tasks.md`；参与服务：`tasks.md` |

拿不准时按高一档处理。

## 5. 流程

```
L1/L2:  ① 需求澄清 ─► ② 写 spec ─► ③ 拆任务(L2) ─► ④ Draft MR 评审 ─► ⑤ 实现(每任务一次) ─► ⑥ MR 合并 ─► ⑦ 归档
        └──── 同一个会话 ────┘                                    └─ 每个任务一个新会话 ─┘
```

**上下文要求**：

- ①② 必须在同一个 AI 会话里连续完成，这样 spec 直接建立在原始讨论上，而不是建立在摘要上。
- ③ 优先在同一个会话里完成。需求涉及的服务多、会话过长时，可以先用 `/sdd-handoff` 生成交接文档，再开新会话拆任务。
- ⑤ 每个任务开一个新会话，只凭 spec 和任务描述工作。

| 阶段 | 命令 | 输入 | 产出 | 完成标准 |
|---|---|---|---|---|
| ① 需求澄清 | `/sdd-grill` | 需求单号和描述、目标版本、现状规格、术语表 | 档位、主服务、feature 分支、共识；更新的术语表和 ADR | 决策树里没有未决问题，开发者确认共识 |
| ② 写 spec | `/sdd-spec` | 本会话的共识 | `spec.md`，L2 加 `design.md` | 测试接缝和验证方式已确认；每条需求有编号且可验证；"待确认问题"为空 |
| ③ 拆任务 | `/sdd-tasks` | spec、design | 各服务的 `tasks.md` | 每条需求都被任务覆盖；开发者确认粒度和依赖 |
| ④ 评审 | 人工 | 各服务的 Draft MR | 评审意见、修订后的文档；状态改为"已确认" | 第 6.1 节的检查项全部通过 |
| ⑤ 实现 | `/sdd-implement` | spec、本任务 | 代码、测试或降级验证脚本、更新后的现状规格 | 第 5.3 节的完成标准 |
| ⑥ 合并 | 人工 | MR | 合并到 `develop-v<目标版本>` | 第 6.3、6.4 节通过 |
| ⑦ 归档 | 人工 | 已发布的需求 | 状态改为"已上线"，变更目录移到 `docs/changes/archive/<年份>/` | 目标版本发布后，在下一个版本的开发周期内完成 |

各阶段的具体步骤见 `skills/<命令名>/SKILL.md`，AI 按这些步骤执行，开发者也可以照着手动执行。

### 5.1 写 spec 的要求

- 写明目标版本。
- 需求用 EARS 句式，每条编号（R1、R2……），每条都能验证：`WHEN <条件>，THE SYSTEM SHALL <行为>`。
- "不做"一节必须有内容，没有就写"无"。
- 写明测试接缝和每个接缝的验证方式：自动化测试，或者降级验证。服务的测试基座为"无"时，必须在这里声明降级验证。
- 用业务语言写，不写具体文件路径和代码片段。表结构、状态机、接口字段这类用代码表达更准确的决策可以摘录关键部分。
- 接口字段明细以接口文档平台为准，spec 和 design 只写变更要点和兼容性。

### 5.2 拆任务的要求

- 每个任务是一条垂直切片，一次会话能做完。
- 预重构任务排在最前。
- 任务编号在整个需求内统一，阻塞依赖可以跨服务，并且和上线顺序一致。

### 5.3 实现的要求

- 测试先行：在确认过的接缝上，一次写一个失败的测试，再写刚好让它通过的代码。只 mock 服务边界之外的依赖。
- 服务没有可用测试基座时，按 spec 声明的降级方式验证：写可重复执行的验证脚本，先确认它能暴露问题，再实现。
- 实现范围以 spec 和任务为准；必须偏离时，先改 spec。
- 业务行为变化时，在同一个 MR 里更新对应能力已有的现状规格，并追加变更记录。这条对所有档位都适用，包括 L0；L0 改到的能力还没有现状规格时，试点期不强制补写，在 MR 里注明即可。接口变化时，同步到接口文档平台。

**完成标准**：

| 服务的测试基座 | 完成标准 |
|---|---|
| 全量 | 约定接缝上的测试通过，全量测试通过 |
| 部分 | 约定接缝上的测试通过，受影响模块编译通过 |
| 无 | spec 声明的降级验证通过，受影响模块编译通过 |

三种情况都要在 MR 里列出没有被验证覆盖的部分。

## 6. 评审

### 6.1 spec 评审（写代码之前）

在 feature 分支上先只提交文档，开 Draft MR。主服务的 MR 评审 spec、design、tasks，参与服务的 MR 评审各自的 tasks。检查项：

- [ ] 目标版本明确
- [ ] "不做"清单明确
- [ ] 每条需求都能验证
- [ ] 测试接缝和验证方式合理；声明了降级验证的，理由成立
- [ ] 待确认问题已清空
- [ ] （L2）服务影响矩阵完整，各服务的目标分支明确，上线顺序和回滚方案可行
- [ ] （L2）任务依赖和上线顺序一致

主服务和所有参与服务的 Draft MR 都通过评审后，需求负责人把 spec 状态改为"已确认"，然后在同一个分支上继续写代码，spec 和代码最终在同一个 MR 里合并。

### 6.2 两轴自审

每个任务完成后，由 AI 运行 `sdd-review`（`/sdd-implement` 会自动调用）：

- **Standards**：对照 `docs/coding-standards.md`、服务 `AGENTS.md` 里的编码约定，以及一组代码坏味道基线
- **Spec**：漏做的需求、范围蔓延、实现错误、现状规格没有同步、声明的验证方式没有落实

两个方向分开报告。审查发现的问题，要么修复，要么在 MR 里说明不修复的理由。

两轴自审是提交给人评审之前的第一遍过滤，**不构成合并条件**；合并与否由第 6.4 节的代码评审决定。

### 6.3 提 MR 前的校验

提 MR 前，在服务目录下运行 `../sdd-standard/scripts/check-spec.sh`。脚本检查：

- feature 分支对应的变更 spec 目录存在，状态取值合法；spec 还没"已确认"就出现代码改动时报错
- 代码有改动但现状规格没有变化时给出提醒（是否涉及业务行为由人判断）
- 现状规格文件都已登记到索引，文件和目录命名符合规则

报错必须处理后才能提交评审；提醒由 MR 作者判断，并在 MR 里说明。

### 6.4 代码评审（合并之前）

reviewer 对照 spec 和 MR 模板里的自查项评审。重点看两轴自审覆盖不了的部分：业务正确性、上线风险、没有被验证覆盖的部分是否可以接受。

## 7. 术语表与 ADR

- **术语表**：核心域服务必须维护 `GLOSSARY.md`，其他服务按需创建。核心域的范围由架构师确认，初步包括设备、家庭、分享、用户、外部集成相关的服务。一个概念只保留一个用词；需求澄清时发现术语冲突，当场确定并写入。格式和规则见 `skills/sdd-domain/SKILL.md`。
- **ADR**：同时满足"难以撤销""没有上下文会让人意外""确实经过取舍"三个条件才写，一段话即可。跨服务决策放规则仓库的 `docs/adr/`，服务内部决策放服务的 `docs/adr/`。
- 写 spec 或代码时与已有 ADR 冲突，必须明确指出，不能悄悄推翻。

## 8. Git 与 MR 约定

- **分支**：feature 分支从 `develop-v<目标版本>` 拉出，命名为 `feature/<需求单号>-<英文短描述>`，同一个需求在各服务使用相同的分支名。修复分支从需要修复的版本分支拉出，命名为 `fix/<需求单号>-<英文短描述>`，L0 没有需求单号时用 `fix/<英文短描述>`。
- **MR**：合并回拉出它的版本分支。使用服务仓库的 MR 模板（来自 `templates/service/merge_request.md`）。参与服务的 MR 描述里用 `<主服务名>:<需求目录名>` 引用主服务 spec。
- **commit**：沿用团队现有格式，必须带需求单号（有的话）和改动类型（feat、fix、refactor、docs、test、chore），说明可以用中文，不要求 scope。需求单号写在最前面，用 `%` 前缀关联需求系统：

  ```
  %184945 feat：车企通知与设备消息订阅增加Apollo开关并默认关闭
  %18978 feat：【平台】首页设备列表计数优化
  %17100 fix: 调整鉴权
  ```

  约定如下：`%<需求单号> <改动类型>：<中文说明>`。冒号全角、半角都可以，团队现状以全角为主，不强制统一。GitLab 生成的合并提交（如 `%CloudCamera-18544 Merge 'feat-xxx' into 'develop-v6.10.1'`）不套用本格式。

- **存量**：已有的 commit、分支和文档不做迁移，本节只约束新的需求。

## 9. 与既有体系的关系

SDD 规范只规定**需求文档层**（spec 写什么、放在哪、怎么评审）和质量关口，不替换团队已有的任务分档、工具链和 AI 工具配置。两者重叠时按下面的顺序处理：

1. **服务仓库自己的工程约定优先**：服务 `AGENTS.md`、构建配置、既有 skill 或 agent 规定的编码方式和工具用法，优先于本规范里的通用编码要求。
2. **需求文档相关的环节使用 `sdd-*` skill**：需求澄清、写 spec、拆任务、对照 spec 审查。其他环节沿用既有工具。
3. **已经使用 OpenSpec 的服务**：保留 `openspec/` 结构，按[管理规范](spec-management.md)第 8 节的对应关系执行，不迁移。
4. **既有任务分档**：和 L0、L1、L2 的对应关系见下表。既有分档来自根 `AGENTS.md` 的工作流车道，按"文件数 → 模块数 → 风险"判定。

| 既有分档 | 判定依据 | 对应的 SDD 档位 | 说明 |
|---|---|---|---|
| 🟢 简单 | 不超过 3 个文件、单模块、无架构风险 | L0 或 L1 | bug、配置、格式调整按 L0；有行为变化按 L1 |
| 🟡 标准 | 3～10 个文件、可能有兼容性风险 | L1 或 L2 | 按第 4 节判断：跨服务、不兼容的接口变更、表结构变更、有上线顺序依赖 → L2；其余 L1 |
| 🔴 专家团 | 超过 10 个文件，或跨模块，或架构决策，或外部集成 | L1 或 L2 | 仍按第 4 节判断：改动量大但单服务且向后兼容 → L1；跨服务或涉及不兼容变更、表结构 → L2。专家团的领域审查结论并入第 6.1 节的 spec 评审，不另增一次评审环节 |

**两者判断不一致时，以第 4 节为准。** 既有分档决定"改动有多大、谁参与"，只影响评审角色；SDD 分档决定"要不要写 spec、写几份"，只影响文档和评审范围。例如单服务内超过 10 个文件、只涉及向后兼容的接口新增：既有分档进专家团车道，SDD 档位仍是 L1。

## 10. AI 工具

- 工作空间根目录的 `AGENTS.md` 和 `CLAUDE.md` 指向规则仓库的 `AGENTS.md`。Claude Code 通过 `CLAUDE.md` 读取，其他主流工具读 `AGENTS.md`。
- skill 放在规则仓库的 `skills/`，由 `scripts/link-skills.sh` 软链到个人目录（`~/.claude/skills`、`~/.agents/skills`），`git pull` 即可更新。
- 所用工具不支持 skill，或不支持 skill 之间互相调用时，直接让 AI 读 `skills/<名称>/SKILL.md` 并按步骤执行，效果相同。
- 工作空间里有代码索引或代码图工具的，AI 在探索代码时优先使用。
- AI 只负责起草和实现，评审结论由人做出。

skill 分三类：

| 类别 | skill | 怎么触发 | 用途 |
|---|---|---|---|
| 阶段 | `sdd-grill`、`sdd-spec`、`sdd-tasks`、`sdd-implement` | 开发者输入命令 | 编排第 5 节的四个 AI 阶段 |
| 方法 | `sdd-interview` | AI 自动调用，也可单独使用 | 多轮决策树提问 |
| 方法 | `sdd-domain` | 同上 | 维护术语表和 ADR |
| 方法 | `sdd-tdd` | 同上 | 测试先行开发，包括降级验证 |
| 方法 | `sdd-review` | 同上 | 两轴自审 |
| 方法 | `sdd-diagnose` | 同上 | 疑难 bug 和性能退化的诊断 |
| 工具 | `sdd-questionnaire` | 开发者输入命令 | 把需要产品或业务方决定的问题整理成问卷 |
| 工具 | `sdd-handoff` | 开发者输入命令 | 把会话整理成交接文档，换工具、换会话或转交同事时使用 |
| 工具 | `sdd-retro` | 开发者输入命令 | 需求或会话结束后复盘，提出规则和模板的改进建议 |

阶段 skill 内部会调用方法 skill：`sdd-grill` 调用 `sdd-interview` 和 `sdd-domain`，`sdd-implement` 调用 `sdd-tdd` 和 `sdd-review`。每种方法只在一个 skill 里定义。
