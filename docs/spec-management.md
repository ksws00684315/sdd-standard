# 服务仓库 spec 管理规范

本文件规定每个服务仓库里的 spec 文档怎么组织、命名、维护和归档，是[团队 SDD 规范](standard.md)的组成部分。已经使用 OpenSpec 的服务，按第 8 节的对应关系执行。

服务仓库里有两类 spec：

| 类型 | 回答的问题 | 位置 | 生命周期 |
|---|---|---|---|
| **变更 spec** | 这次要改什么 | `docs/changes/<需求目录>/` | 随需求产生，目标版本发布后归档，归档后只修正错别字和链接 |
| **现状规格** | 系统现在是什么样 | `docs/specs/<能力>.md` | 长期存在，随代码一起合并，描述它所在分支上的代码 |

## 1. 目录结构

```
<服务>/
├── AGENTS.md / CLAUDE.md
├── GLOSSARY.md                          领域术语（核心域服务必须有，其他按需）
├── .gitlab/merge_request_templates/Default.md
└── docs/
    ├── specs/                           现状规格
    │   ├── README.md                    能力索引
    │   ├── order-lifecycle.md           一个业务能力一个文件
    │   └── order-pricing.md
    ├── adr/                             本服务内部的架构决策（需要时创建）
    │   └── 0001-<描述>.md
    └── changes/                         变更 spec
        ├── REQ-12345-order-timeout-cancel/    进行中的需求
        │   ├── spec.md                  主服务、单服务需求才有
        │   ├── design.md                L2 主服务才有
        │   ├── tasks.md                 L2，或 L1 拆了任务时
        │   ├── verify/                  声明了降级验证时，放验证脚本
        │   └── questionnaire-<主题>.md  需要时
        └── archive/
            └── 2026/                    按目标版本发布的年份分组
                └── REQ-10001-.../
```

SDD 只使用 `docs/` 下的这三个目录。服务原有的其他文档（部署说明等）可以继续放在 `docs/` 的其他子目录里，但不能和这三个目录同名。

## 2. 命名

| 对象 | 规则 | 例子 |
|---|---|---|
| 需求目录 | `<需求单号>-<英文短描述>`，短描述用小写英文和连字符，3～5 个单词 | `REQ-12345-order-timeout-cancel` |
| feature 分支 | `feature/` 加上需求目录名，从 `develop-v<目标版本>` 拉出，各服务相同 | `feature/REQ-12345-order-timeout-cancel` |
| 现状规格文件 | `<能力英文名>.md`，小写英文和连字符 | `order-lifecycle.md` |
| 问卷 | `questionnaire-<英文主题>.md`，放在需求目录里 | `questionnaire-refund-rules.md` |
| ADR | `NNNN-<英文短描述>.md`，编号在所在目录递增 | `0002-order-events-via-mq.md` |

- 文件名和目录名一律用英文；文件里的标题和正文用中文。
- 一个需求在一个服务里只有一个目录。不同需求不共用目录。
- 需求单号是需求系统里的纯数字，commit 里写作 `%<单号>`（`%` 和项目前缀不属于单号），所以真实的需求目录名形如 `18544-add-icon`。本仓库示例沿用 `REQ-0000` 这种带前缀的写法，两种都符合命名规则。
- 需求单号保证需求目录名在全团队唯一，所以"服务名 + 需求目录名"可以唯一定位一份变更 spec。

## 3. 变更 spec

### 3.1 各文件放在哪个服务

| 文件 | 单服务需求（L1） | 跨服务需求（L2）主服务 | 跨服务需求（L2）参与服务 |
|---|---|---|---|
| `spec.md` | 有 | 有 | 无 |
| `design.md` | 无 | 有 | 无 |
| `tasks.md` | 一次会话做不完时有 | 有，只列本服务任务 | 有，只列本服务任务 |
| `verify/` | 声明了降级验证时有 | 同左 | 同左 |

### 3.2 状态

状态只记录在 `spec.md` 头部的"状态"字段。参与服务的 `tasks.md` 不记录状态，以主服务为准。

| 状态 | 含义 | 何时改 | 谁改 |
|---|---|---|---|
| 草稿 | 正在编写 | `/sdd-spec` 生成时 | AI |
| 评审中 | 已提交，等待评审 | 开 Draft MR 时 | 需求负责人 |
| 已确认 | 评审通过，可以开始实现 | 主服务和所有参与服务的 Draft MR，spec 评审项都已通过时 | 需求负责人 |
| 已上线 | 目标版本已发布 | `release-v<目标版本>` 发布后，归档时一并修改 | 需求负责人 |
| 已中止 | 需求取消 | 确认取消时 | 需求负责人 |

### 3.3 职责

- **需求负责人**（负责该需求的开发者）：维护该需求在所有涉及服务里的变更 spec，推进状态，负责归档。
- **评审人**：评审 spec。试点期建议：L1 由该服务负责人评审，L2 再加上架构师。
- 一个需求只有一个需求负责人，即使它跨多个服务。

### 3.4 评审通过后，需求有变化

状态到"已确认"之后，需求、验收条件、接口、上线顺序、目标版本的任何变化：

1. 先改 `spec.md`（或 `design.md`），同步调整受影响的 `tasks.md`。
2. 在 `spec.md` 末尾的"变更记录"里追加一行：日期、改了什么、为什么、谁确认的。
3. 评审人对这部分 diff 重新确认。

错别字、格式这类不影响含义的修改，不用记录。

### 3.5 需求中止

- 还没有任何服务合并：状态改为"已中止"，在"变更记录"里写明原因；文档留在未合并的分支上，分支可以删除。
- 已有服务合并了部分代码：状态改为"已中止"，写明原因，以及已合并的代码怎么处理（回滚、用开关关闭或保留），由技术负责人决定。然后按第 5 节归档，归档到中止当年的目录。

### 3.6 跨服务引用

参与服务的 `tasks.md`、MR 描述、跨服务的阻塞依赖，引用其他服务的 spec 时写成：

```
<服务名>:<需求目录名>
例：order-service:REQ-12345-order-timeout-cancel
```

可以另外附上 GitLab 链接方便点击，但以"服务名 + 需求目录名"为准。这样不论 spec 在 feature 分支、版本分支，还是已经移到归档目录，都能按目录名找到。

### 3.7 涉及的服务不在同一个版本上

跨服务需求涉及的某个服务，如果没有 `develop-v<目标版本>` 分支（还停在更早的版本上），需求负责人要和该服务负责人确认它的目标分支，写进 `design.md` 服务影响矩阵的"目标分支"一列。该服务的 feature 分支从这个目标分支拉出，MR 也合并回它。

## 4. 现状规格

### 4.1 按业务能力组织

- 一个业务能力一个文件。业务能力是指从业务角度能说清楚的一块功能，比如"订单状态流转""订单计价""库存锁定与释放"，而不是一个 Controller 或一张表。
- 一个文件超过大约 300 行，或者明显包含两块可以独立理解的功能时，拆开。
- `docs/specs/README.md` 是索引，每个能力一行。新增、拆分、删除能力文件时同步更新索引。

### 4.2 写什么，不写什么

| 写 | 不写 |
|---|---|
| 当前的业务规则，用 EARS 句式 | 规则是怎么一步步变成现在这样的（这部分看变更记录和归档的变更 spec） |
| 对外接口的用途，字段明细链接到接口文档平台 | 完整的请求、响应字段 |
| 主要的表和关键字段的业务含义 | 类名、方法名、文件路径 |
| 变更记录：哪些需求改过这个能力 | 还没合并到本分支的规则 |

**现状规格以所在分支为准**：它和代码放在同一个仓库、同一个分支里，描述的就是这个分支上的代码。规则随代码合并进分支时写入，不等发布。版本分支之间的合并（例如 `release` 合回 `master`、修复合并到新版本的 `develop`）会把现状规格和代码一起带过去。

已合并但被开关关闭的规则也要写，并注明"受开关 <名称> 控制"；开关最终移除时，同步去掉这个注明。

格式见规则仓库的 `templates/service/capability-spec.md`。

### 4.3 什么时候必须更新

- **任何**改变业务行为的 MR，都要在同一个 MR 里更新对应能力已有的现状规格，包括 L0 的 bug 修复和小调整。档位只决定要不要写变更 spec，不影响这项更新义务。
- 更新时，在该能力文件末尾的"变更记录"里追加一行：需求单号和一句话说明。L0 改动没有需求单号时，写 MR 编号。
- L1、L2 需求涉及的能力还没有现状规格时，先补写这个能力的现状规格（见第 6 节），再写这次的改动。
- L0 改动涉及的能力还没有现状规格时，试点期不强制补写，在 MR 的改动说明里注明"该能力暂无现状规格"。这是试点观察项，正式版的规则根据试点结果确定（见 `rollout-plan.md`）。

### 4.4 职责

- **服务负责人**对本服务现状规格的准确性负责，定期抽查。
- **MR 作者**负责在 MR 里同步更新现状规格；reviewer 按 MR 模板检查。

### 4.5 多个需求同时修改同一个能力

现状规格和代码一样，只在 MR 合并到分支时生效。两个需求同时修改同一个能力文件时，后合并的 MR 先同步目标分支，按普通代码冲突的方式合并两边的修改，reviewer 确认合并后的规则是对的。

## 5. 归档

- **时机**：目标版本发布（`release-v<目标版本>` 上线）后，在下一个版本的开发周期内完成；需求中止的，在中止后完成。
- **操作**：需求负责人在下一个版本的 `develop` 分支上，先把 `spec.md` 的状态改为"已上线"（或"已中止"），再把每个服务里的需求目录移到 `docs/changes/archive/<年份>/`，年份按目标版本发布（或中止）的年份算。用 `git mv` 移动，保留历史。
- **方式**：可以顺带放在该服务的下一个 MR 里，不需要单独提 MR。
- **旧版本分支**：已经发布的版本分支上，需求目录保持原位，不需要回头归档。
- **归档后**：只允许修正链接、错别字，不再修改内容。同一个能力后续有新的变化，走新的需求。
- 这样 `docs/changes/` 下只剩进行中的需求，一眼就能看到这个服务手上有哪些需求。

## 6. 存量

- 已有的需求文档、设计文档（飞书、Confluence 等）**不迁移**，保持原样。
- 已有的 commit、分支不做调整，命名和格式要求只约束新的需求。
- 第一次有需求改到某个能力时，参考代码和旧文档补写这个能力的现状规格：可以让 AI 先读代码起草，再由熟悉业务的人校对。在现状规格的"参考资料"里附上旧文档的链接。
- 不要求在接入时一次补齐所有能力。

## 7. 检查清单

提 MR 前运行规则仓库的 `scripts/check-spec.sh`，它能自动检查下面标了"脚本"的项目。服务负责人在 MR 评审和定期抽查时使用整份清单：

- [ ] （脚本）feature 分支对应的变更 spec 目录存在，状态取值合法
- [ ] （脚本）spec 还没"已确认"时，没有代码改动
- [ ] （脚本提醒）代码有改动时，已确认是否需要更新现状规格
- [ ] （脚本）现状规格文件都已登记到 `docs/specs/README.md`
- [ ] （脚本）文件名、目录名符合第 2 节的命名规则（只校验本次分支新增的目录）
- [ ] `docs/changes/` 下的每个目录都对应一个进行中的需求
- [ ] 本次 MR 改变的业务行为，在现状规格里有对应更新和变更记录

## 8. 已使用 OpenSpec 的服务

已经使用 OpenSpec 的服务保留 `openspec/` 目录结构，不迁移。流程、分档、评审、状态等规则和其他服务完全相同，只是文件位置按下表对应：

| 本规范 | OpenSpec 服务中的位置 | 说明 |
|---|---|---|
| `docs/changes/<需求目录>/` | `openspec/changes/<需求目录>/` | change id 使用同样的 `<需求单号>-<英文短描述>` |
| `spec.md` 的头部字段、背景、范围、不做、非功能要求、测试接缝、待确认问题、变更记录 | `proposal.md` | 头部字段（需求单、档位、目标版本、涉及服务、需求负责人、状态）放在最前面 |
| `spec.md` 的需求与验收条件 | `openspec/changes/<需求目录>/specs/<能力>/spec.md` | 每个 Requirement 的标题以需求编号开头，如 `R1 超时未支付自动取消`；验收条件写成 Scenario |
| `design.md` | `design.md` | — |
| `tasks.md` | `tasks.md` | 每个任务前加上需求内统一的 T 编号，方便跨服务引用 |
| `docs/specs/<能力>.md` | `openspec/specs/<能力>/spec.md` | 不另建 `README.md` 索引 |
| 现状规格的变更记录 | 不另写 | 以 `openspec/changes/archive/` 为准 |
| `docs/changes/archive/<年份>/` | `openspec/changes/archive/<日期>-<需求目录>/` | 由 `openspec archive` 生成 |

两点差异：

- **归档时机**：OpenSpec 在归档时才把变更合入现状规格。为了让现状规格随代码一起合并，OpenSpec 服务在 MR 合并前执行 `openspec archive <需求目录>`，让归档和代码在同一个 MR 里合并。目标版本发布后，再把归档目录里 `proposal.md` 的状态改为"已上线"，这是归档后唯一允许的内容修改。
- **作为参与服务时**：OpenSpec 要求每个 change 都有 `proposal.md`。参与服务的 `proposal.md` 只写头部字段和一行"主 spec：`<主服务名>:<需求目录名>`"，任务写在 `tasks.md` 里。

**`openspec` 命令不可用时**：没装 CLI 的机器上，按下面的等价操作手动归档，随 MR 一起提交。

1. `git mv openspec/changes/<需求目录> openspec/changes/archive/<YYYY-MM-DD>-<需求目录>`
2. 把这个 change 在 `specs/<能力>/spec.md` 里的 Requirement 和 Scenario 合入 `openspec/specs/<能力>/spec.md`；新能力则新建 `<能力>/spec.md`。
3. 目标版本发布后，把归档目录里 `proposal.md` 的状态改为"已上线"。

接入时的存量 change 目录（例如归档前没有需求单号的 change id）不要求改名：`check-spec.sh` 只校验本次分支新增的目录，存量目录按第 6 节"不迁移"处理。

OpenSpec 自带的命令（如 `openspec validate`）可以继续使用。
