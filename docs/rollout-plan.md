# 试点与推广计划

先让少数人用真实需求跑通流程，根据反馈修订规范，再逐步扩大。每个阶段都要达到退出条件，才进入下一阶段。

## 阶段 0：准备（约 1 周）

| 事项 | 负责人 |
|---|---|
| 填写 `AGENTS.md` 服务地图（含各服务的测试基座）、`repos.txt`、`GLOSSARY-MAP.md` | TODO |
| 在 `docs/coding-standards.md` 补充团队在《阿里巴巴 Java 开发手册》之外的条目 | TODO |
| 把需求单号的实际格式替换进规范、skill、示例和 `scripts/check-spec.sh`（目前用 `REQ-12345`、`REQ-0000` 占位） | TODO |
| 补充团队现有的 commit 格式，以及既有任务分档和 L0、L1、L2 的对应关系（规范第 8、9 节） | TODO |
| 架构师评审本规范，在规则仓库合并 | TODO |
| 规则仓库迁移到公司 GitLab | TODO |
| 选定试点人员和试点需求，按[服务接入清单](service-onboarding.md)接入涉及的服务，确认每个服务的测试基座 | TODO |
| 在试点涉及的每个服务里运行 `scripts/check-spec.sh`，确认能正常输出结果 | TODO |

退出条件：规范已合并；试点涉及的服务已接入，且都能编译并单独运行测试类（没有测试的服务已标为"无"）；`check-spec.sh` 能在试点服务上运行；试点人员完成了[上手指南](getting-started.md)第 1、2 节。

## 阶段 1：试点（2～3 周）

- 人员：1～2 人，最好有一人用 Claude Code，另一人用其他 AI 工具，同时验证跨工具的可用性。
- 需求：1 个 L2 跨服务需求，加 1～2 个 L1 需求。其中至少有一个需求涉及测试基座为"无"的服务，用来验证降级验证是否可行。
- 每个需求完成后，花 15 分钟复盘：运行 `/sdd-retro` 让 AI 提出改进建议，再回答下面的复盘问题。

退出条件：试点需求全部上线；根据复盘修订出下一版规范。

## 阶段 2：扩大到一个小组（约 1 个月）

- 小组内所有 L1、L2 需求按规范执行。
- 试点人员担任答疑人。
- 每两周汇总一次复盘记录，修订规范。

退出条件：评估指标没有明显恶化；小组成员认可后，发布 v1.0。

## 阶段 3：全团队推行

- 所有服务按接入清单接入。
- MR 模板里的检查项作为合并条件。
- 规范修订改为按需进行，通过规则仓库的 MR 提出。

## 试点观察项

下面这些规则在当前版本里只是默认做法，还没有经过实践验证。试点期间按默认规则执行，同时记录观察结果；试点结束时逐项给出结论，写进下一版规范。

| 观察项 | 试点期默认规则 | 观察什么 | 正式版要决定什么 |
|---|---|---|---|
| L0 改到没有现状规格的能力 | 不强制补写，在 MR 里注明"该能力暂无现状规格" | 这种注明出现的次数；之后 L1、L2 改到同一能力时，补写的成本有多高 | 正式版是否强制补写，或者按改动大小设门槛 |
| 评审人分工 | L1 由服务负责人评审，L2 再加架构师 | 从开 Draft MR 到评审通过的耗时；架构师是否成为瓶颈 | 正式的评审人分工 |
| 状态手动切换 | 需求负责人手动修改"评审中""已确认""已上线" | 抽查时，状态和实际进度不一致的次数 | 是否需要脚本或 CI 检查状态 |
| 归档时机 | 目标版本发布后，在下一个版本的开发周期内，顺带放在该服务的下一个 MR 里 | 进入下一个版本后仍未归档的需求数 | 是否要求单独提 MR，或者在 `check-spec.sh` 里检查 |
| skill 互相调用和跨工具 | 工具不支持 skill 之间调用时，让 AI 直接读对应的 `SKILL.md` | 在 Claude Code 以外的工具里，阶段 skill 能不能正确用上方法 skill | 是否把方法内容内联回阶段 skill |
| 参与服务的跨仓库操作 | 用 `git show` 读取主服务的 spec；spec 的修改由需求负责人提交到主服务分支 | 跨仓库操作出错或卡住的次数 | 是否需要辅助脚本 |
| ③ 拆任务换会话 | ①② 必须同一会话；③ 可以用 `/sdd-handoff` 换新会话 | 换会话后拆出的任务质量是否下降 | 维持还是收紧 |
| 现状规格以所在分支为准 | 规则随代码合并进分支即写入；被开关关闭的规则注明开关名 | 版本分支之间合并时规格是否冲突；开关类规则是否被正确标注 | 维持还是调整 |
| 降级验证 | 测试基座为"无"的服务，在 spec 里事先声明，用 `verify/` 下的脚本验证 | 降级验证能否发现真实问题；声明降级的接缝占比 | 是否需要在接入时强制补齐测试基座 |
| 提 MR 前的校验 | `check-spec.sh` 报错必须处理，提醒由人判断 | 误报和漏报的次数；"代码改了但规格没改"的提醒里，真正需要更新的比例 | 哪些检查可以升级为报错，是否接入 CI |
| OpenSpec 服务并存 | 保留 `openspec/` 结构，按对应表执行 | OpenSpec 服务和其他服务一起参与跨服务需求时是否顺畅 | 维持并存，还是收敛到一套目录结构 |

## 评估指标

| 指标 | 怎么统计 | 期望趋势 |
|---|---|---|
| spec 评审中发现的问题数 | Draft MR 上的评审意见数 | 早期多是好事，说明问题在写代码前就被发现了 |
| 代码 MR 被打回的次数 | MR 记录 | 下降 |
| 上线后因需求理解偏差导致的缺陷 | 缺陷记录中标注"需求理解"的数量 | 下降 |
| spec 和代码的一致性 | 每月抽查 2～3 个已上线需求，对照 spec 和实际行为 | 一致 |
| 开发者感受到的耗时 | 复盘时询问：比原来的做法快、持平还是慢，慢在哪里 | 持平或更快 |

## 复盘问题（每个需求完成后填写）

1. 需求档位判断得对吗？流程对这个需求来说是太重、刚好，还是太轻？
2. 需求拷问漏掉了什么，导致后面返工？
3. 哪一步最耗时？是 AI 的问题、模板的问题，还是规范的问题？
4. AI 有没有偏离流程（跳过提问、超出 spec 实现、没有停下）？当时它在什么情况下？
5. 两轴审查发现了真问题，还是主要是噪音？
6. 如果只能改规范的一处，你会改什么？

复盘记录集中放在规则仓库的 `docs/rollout/` 目录下（第一次记录时创建），每个需求一个文件，作为修订规范的依据。
