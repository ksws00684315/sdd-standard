# SDD 拆任务

## 步骤

### 1. 读 spec

读主服务的 `spec.md` 和 `design.md`，通常就是本会话刚写的那两份；如果是用 `/sdd-handoff` 换到新会话的，先读交接文档。浏览涉及服务的相关代码（有代码索引或代码图工具的优先使用），找出能让实现更容易的**预重构**："先让改动变容易，再做这个容易的改动"。

### 2. 按垂直切片拆分

每个任务是一条**垂直切片**：

- 贯穿所需的各层（表结构、Mapper、Service、接口、测试），交付一段完整、可以单独验证的行为。按行为切，而不是按层切成"先写完所有 DAO，再写所有 Service"。
- 大小放得进一个全新的会话，一次会话就能做完。
- 预重构任务排在最前面。
- 每个任务标注覆盖的需求编号（R1、R2……）。

例外：大范围的机械性改动（改字段名、换公共类型）一次改不完，中间又要保持代码能编译、测试能通过时，按"扩展 → 分批迁移 → 收缩"来排：先加上新形式并保留旧形式；再分批把调用方迁过去，每批一个任务；最后删掉旧形式，这个任务被所有迁移任务阻塞。

### 3. 标注阻塞依赖

- 每个任务写明被哪些任务阻塞，可以跨服务，例如 `inventory-service T1`。没有阻塞的写"无"。
- 任务编号在整个需求内统一（T1、T2……），不按服务重新编号，方便跨服务引用。
- 跨服务的依赖要和 `design.md` 里的上线顺序一致。

### 4. 请用户确认

用编号列表展示拆分结果，每个任务列出：所属服务、标题、被谁阻塞、交付什么行为。请用户确认：

- 粒度是否合适（太粗还是太细）
- 依赖关系是否准确：每个依赖是否真的必须先完成
- 是否需要合并或继续拆分

反复调整，直到用户确认。

### 5. 写入文件

按 [templates/tasks.md](templates/tasks.md)，在每个涉及的服务里写各自的 `tasks.md`，只列本服务的任务：

- 主服务：`<主服务>/docs/changes/<需求目录>/tasks.md`
- 参与服务：`<参与服务>/docs/changes/<需求目录>/tasks.md`，开头用 `<主服务名>:<需求目录名>` 的格式引用主服务 spec，可以附 GitLab 链接

参与服务的文档也写在同名的 feature 分支上，这个分支从该服务的目标分支拉出（见 `design.md` 服务影响矩阵）。参与服务当前不在这个分支上时，告诉用户，用户同意后再切换或创建。

服务根目录有 `openspec/` 时，按规则仓库 `docs/spec-management.md` 第 8 节写到 `openspec/changes/<需求目录>/tasks.md`；作为参与服务时，还要写一份只含头部字段和主 spec 引用的 `proposal.md`。

完成标准：spec 里的每条需求都至少被一个任务覆盖。

### 6. 结束

提示用户：

1. 在各服务的 feature 分支上提交文档，开 Draft MR 评审，并把主服务 spec 的状态改为"评审中"。主服务的 MR 评审 spec、design、tasks；参与服务的 MR 评审各自的 tasks。
2. 所有 Draft MR 都通过评审后，把 spec 状态改为"已确认"。然后按依赖顺序，每个任务开一个新会话，运行 `/sdd-implement <服务> T<编号>`。
