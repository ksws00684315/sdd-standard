# SDD 两轴审查

对 `HEAD` 和一个基准点之间的改动，从两个方向审查：

- **Standards**：代码是否符合团队和本服务的编码规范
- **Spec**：代码是否忠实实现了 spec

两个方向分开审查、分开报告。代码可能完全符合规范却做错了事，也可能做对了事却破坏了规范；分开才不会让一个方向的问题掩盖另一个。

## 步骤

### 1. 确定基准点

用用户给的基准点（分支、commit、tag）。没给时，用 `git merge-base origin/<目标分支> HEAD`：目标分支一般是 `develop-v<目标版本>`（目标版本写在 spec 头部），`design.md` 服务影响矩阵另有写明的以矩阵为准。确定不了目标分支时就问。

- 差异命令：`git diff <基准点>...HEAD`（三个点，和分叉点比较）
- 提交列表：`git log <基准点>..HEAD --oneline`
- 先确认 `git rev-parse <基准点>` 能解析、差异不为空；不满足就在这一步报错。

### 2. 找 spec

按顺序找：

1. 用户给的路径
2. 分支名或 commit 里的需求单号对应的 `docs/changes/<需求单号>-*/`；不在那里时，查 `docs/changes/archive/*/`
3. 参与服务的 `tasks.md` 里以 `<主服务名>:<需求目录名>` 引用的主服务 spec，在该服务的 `docs/changes/` 或 `docs/changes/archive/*/` 下按目录名查找

服务根目录有 `openspec/` 时，按规则仓库 `docs/spec-management.md` 第 8 节的对应关系，在 `openspec/changes/` 和 `openspec/changes/archive/` 下查找。

都找不到就问用户。用户确认没有 spec（L0 改动）时，跳过 Spec 方向，并在报告里注明。

### 3. 找编码规范

- 规则仓库的 `docs/coding-standards.md`。规则仓库是工作空间里和各服务仓库并列的 `sdd-standard/` 目录；只打开了服务仓库时，在 `../sdd-standard/`。
- 本服务 `AGENTS.md` 里的"编码约定"。
- 本服务里其他记录编码规则的文件，例如 `CONTRIBUTING.md`。

此外始终带上下面的**坏味道基线**（出自 Fowler《重构》第 3 章）。两条规则：文档化的规范优先，规范明确允许的就不报；基线里的每一项都是需要判断的提示，不是硬性违规。P3C、checkstyle、编译器等工具已经能拦住的问题不报。

- **含义不明的命名**：名字看不出它做什么、存什么。→ 改名；起不出好名字，说明设计不清楚。
- **重复代码**：同样的逻辑出现在改动的多处。→ 提取公共部分。
- **依恋情结**：方法用别的对象的数据比用自己的还多。→ 把方法移到数据所在的类。
- **数据泥团**：几个字段或参数总是一起出现。→ 合并成一个类型。
- **基本类型偏执**：用 String、Long 代表一个值得有自己类型的业务概念。→ 给它一个小类型。
- **重复的 switch**：对同一类型的 switch 或 if 链在多处出现。→ 用多态或共享的映射替代。
- **霰弹式修改**：一个逻辑改动要散落地改很多文件。→ 把一起变化的东西聚到一个模块。
- **发散式变化**：一个类因为多个不相关的原因被修改。→ 拆开，让每个类只因一个原因变化。
- **夸夸其谈的通用性**：为 spec 里没有的需求加了抽象、参数或扩展点。→ 删掉，等真正需要时再加。
- **过长的消息链**：`a.getB().getC().getD()` 这种调用方不该依赖的导航。→ 在第一个对象上提供一个方法把它藏起来。
- **中间人**：一个类基本只是把调用转给别人。→ 去掉，直接调用真正的目标。
- **被拒绝的遗赠**：子类忽略或重写了继承来的大部分东西。→ 改用组合。

### 4. 两个方向分别审查

工具支持子代理时，同时启动两个子代理，每个都用全新的上下文，然后汇总两份报告。不支持子代理时，依次完成两个方向：做完一个、写下结论，再做另一个。

**Standards 方向**，输入：差异命令、提交列表、第 3 步找到的规范文件、完整的坏味道基线。要求：

> 按文件或代码块报告：(a) 违反文档化规范的地方，注明出处（文件和条目）；(b) 发现的基线坏味道，写出名称并引用代码。区分硬性违规和需要判断的问题：违反文档化规范可以是硬性的，基线坏味道始终是需要判断的。工具已经能拦截的不报。400 字以内。

**Spec 方向**，输入：差异命令、提交列表、spec 路径（`spec.md`、`design.md`、相关的 `tasks.md`）。要求：

> 报告：(a) spec 要求了、但缺失或只做了一部分的需求；(b) spec 没要求、却出现在改动里的行为（范围蔓延）；(c) 看起来实现了、但实现方式不对的需求；(d) 业务行为变了、但 `docs/specs/` 没有同步更新或没有追加变更记录的地方；(e) spec"测试接缝"表声明的验证方式没有落实的地方（声明了自动化测试却没有测试，声明了降级验证却没有可执行的验证脚本）。每条都引用对应的 spec 原文或需求编号。400 字以内。

### 5. 汇总

在 `## Standards` 和 `## Spec` 两个标题下分别给出报告，原样或稍作整理，不合并、不重新排序。

最后用一行总结：每个方向的问题数，以及每个方向里最严重的一条。两个方向各报各的最严重问题，不在两个方向之间比较。
