# 术语表与 ADR

在讨论和设计过程中，主动建立和打磨领域模型：质疑用词、用具体场景检验概念边界，术语和决策一确定就写下来。

只是读术语表来统一用词，不需要这个 skill；这个 skill 用于**修改**领域模型的时候。

## 放在哪

| 内容 | 位置 |
|---|---|
| 某个服务的领域术语 | `<服务>/GLOSSARY.md` |
| 某个服务内部的决策 | `<服务>/docs/adr/` |
| 跨服务的决策（服务间通信方式、数据归属等） | 规则仓库 `docs/adr/` |
| 各服务术语表的索引、服务之间的术语对应关系 | 规则仓库 `GLOSSARY-MAP.md` |

规则仓库就是工作空间根目录。文件在第一次需要写入时才创建；新建某个服务的 `GLOSSARY.md` 时，同时在 `GLOSSARY-MAP.md` 里登记。

服务仓库里的术语表和 ADR，写在当前需求的 feature 分支上，随需求的 MR 一起评审。规则仓库里的改动（`GLOSSARY-MAP.md` 登记、跨服务 ADR）属于另一个仓库，要告诉用户单独在规则仓库提 MR。

## 讨论过程中

- **对照术语表质疑**：用户的用词和 `GLOSSARY.md` 冲突时，当场指出："术语表里'取消'指的是 X，你这里说的好像是 Y，以哪个为准？"
- **把模糊的词变精确**：一个词承担了多种意思时，提出一个精确的规范用词。"你说的'账户'，是指用户（User）还是商户（Merchant）？"
- **用具体场景检验**：讨论概念之间的关系时，构造边界场景，逼出精确的定义。
- **和代码对照**：用户描述的现状和代码不一致时，指出矛盾："代码里取消的是整个订单，但你刚才说可以部分取消，以哪个为准？"
- **当场写入**：术语确定后，马上更新 `GLOSSARY.md`，不要攒到最后。

## 术语表格式

```md
# <服务名>

<一两句话：这个服务负责什么。>

## 术语

**订单（Order）**：
<一两句话，定义它是什么。>
_避免使用_：单据、交易
```

规则：

- 一个概念只保留一个用词，其他说法列在"避免使用"里。
- 定义写"它是什么"，一两句话。
- 只收录本服务特有的业务概念。超时、重试、分页这类通用技术概念不收。
- 术语表只放术语，不放实现细节，也不当 spec 或草稿本用。
- 术语多了以后，按自然形成的类别分小标题。
- 同一个词在不同服务里含义不同时，各自在自己的术语表里定义，并在 `GLOSSARY-MAP.md` 的"服务关系"里注明对应关系。

## ADR

只在同时满足三个条件时，才提议写 ADR：

1. **难以撤销**：以后改主意的代价很大
2. **没有上下文会让人意外**：后来的人看到会问"为什么这么做"
3. **确实经过取舍**：有真实的备选方案，并且出于具体原因选了其中一个

典型的例子：服务之间用消息还是同步调用、某类数据归哪个服务所有、带来锁定效应的技术选型（数据库、消息中间件）、刻意偏离常规做法的选择、代码里看不出来的外部约束。

文件名用 `NNNN-<英文短描述>.md`，编号取所在目录里最大编号加一。内容可以只有一段：

```md
# <决策标题>

<一到三句话：背景、决定了什么、为什么。>
```

只有确实有价值时，才加"状态"（提议中 / 已接受 / 已废弃 / 被 ADR-NNNN 取代）、"备选方案""影响"这几节。示例见规则仓库的 `docs/adr/0001-spec-in-service-repos.md`。

## 和已有 ADR 冲突时

写 spec、方案或代码时，如果和已有 ADR 冲突，要明确写出来，不能悄悄推翻：

> 与 ADR-0003（订单与库存通过 MQ 通信）冲突，建议重新讨论，因为……
