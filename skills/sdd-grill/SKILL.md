# SDD 需求拷问

把一个需求从模糊的想法变成双方确认过的共识。这是 SDD 流程的第 1 步，之后在**同一个会话**里接着运行 `/sdd-spec`（L2 再运行 `/sdd-tasks`），让 spec 直接建立在这次讨论之上。

规则仓库就是工作空间根目录；如果当前只打开了某个服务仓库，规则仓库通常在它的上一级目录。

## 步骤

### 1. 收集上下文

- 需求单号和需求描述由用户提供；没有需求单号时先问。L1、L2 需求必须有需求单号，L0 可以没有。
- 读规则仓库 `AGENTS.md` 里的服务地图，找出可能涉及的服务。
- 读这些服务的 `GLOSSARY.md`、`docs/specs/`、`docs/adr/`，以及规则仓库的 `GLOSSARY-MAP.md` 和 `docs/adr/`。文件不存在就跳过，不用提示。

完成标准：能说出需求涉及哪些服务，以及每个服务现在的相关行为。

### 2. 判断档位

按 `AGENTS.md` 里的分档表判断 L0 / L1 / L2，把结论和理由告诉用户。拿不准时按高一档处理。

- L0：告诉用户不需要写 SDD 文档，直接修改并补测试即可（疑难 bug 可以用 `sdd-diagnose`），然后结束本 skill。
- L2：同时给出建议的主服务（需求发起方或核心服务）和理由。
- L1、L2：给出需求目录名 `<需求单号>-<英文短描述>`（短描述用小写英文和连字符，3～5 个单词）和对应的分支名 `feature/<需求目录名>`。用户同意后，在每个涉及的服务里切到这个分支（不存在就创建）。后面写入的术语表、ADR、问卷和 spec 都落在这个分支上。

完成标准：用户确认了档位；L2 还确认了主服务；L1、L2 涉及的服务都已在 feature 分支上。

### 3. 拷问需求

调用 Skill 工具两次，分别运行 `sdd-interview` 和 `sdd-domain`：前者按决策树逐轮提问，后者在提问过程中维护术语表和 ADR。

后端微服务需求里最容易漏的几类问题，要确保决策树覆盖到：

- 异常与并发：重复请求、并发修改、下游超时或失败
- 跨服务：调用顺序、同步还是异步、一致性怎么保证、谁先上线
- 数据：表结构变化、历史数据要不要迁移
- 范围：哪些明确不做

某个决策需要产品或业务方来定、当场问不到时，记下来，建议用户用 `/sdd-questionnaire` 整理成问卷；其余问题继续推进。

### 4. 结束

决策树里没有未决问题时，用几行话总结共识：档位、涉及服务、主服务、关键决策、不做什么，请用户确认。

完成标准：用户确认共识完整。然后提示用户在同一个会话里运行 `/sdd-spec`。
