# SDD 需求拷问

把一个需求从模糊的想法变成双方确认过的共识。这是 SDD 流程的第 1 步，之后在**同一个会话**里接着运行 `/sdd-spec`（L3、L4 再运行 `/sdd-tasks`），让 spec 直接建立在这次讨论之上。

规则仓库是工作空间里和各服务仓库并列的 `sdd-standard/` 目录；如果当前只打开了某个服务仓库，规则仓库在 `../sdd-standard/`。跨服务需求还要用到治理仓 `../sdd-governance/`。

## 步骤

### 1. 收集上下文

- 需求单号、需求描述和目标版本由用户提供；没有的先问。L2～L4 需求必须有需求单号和目标版本，L1 可以没有需求单号。
- 读规则仓库 `AGENTS.md` 里的服务地图，找出可能涉及的服务。工作空间里有代码索引或代码图工具的，探索代码时优先使用。
- 读这些服务的 `GLOSSARY.md`、`docs/specs/`、`docs/adr/`，以及规则仓库的 `GLOSSARY-MAP.md` 和 `docs/adr/`。文件不存在就跳过，不用提示。

完成标准：能说出需求涉及哪些服务，以及每个服务现在的相关行为。

### 2. 判断档位

按规则仓库 `AGENTS.md` 里的分档表判断 L1～L4，把结论和理由告诉用户。任一维度命中更高档位就按更高档执行，拿不准时按高一档处理。

- **L1**：告诉用户不需要写 SDD 文档，直接修改并补回归测试即可（疑难 bug 可以用 `sdd-diagnose`），然后结束本 skill。修复过程中发现 spec 缺失或错误时，停下来改 spec（重新定档），再修代码。
- **L2～L4**：给出需求目录名 `<需求单号>-<英文短描述>`（短描述用小写英文和连字符，3～5 个单词）和对应的分支名 `feature/<需求目录名>`。检查每个涉及的服务有没有 `develop-v<目标版本>` 分支；没有的，告诉用户，请他和该服务负责人确认这个服务用哪个分支作为目标分支。用户同意后，在每个涉及的服务里从目标分支拉出 feature 分支（已存在就切换过去）。后面写入的术语表、ADR、问卷和 spec 都落在这个分支上。
- **平台仓（已接入研发云数字员工）**：分支、目录、骨架和 item 由平台 init 创建（见规则仓库 `docs/standard.md` 第 5 章），你不创建分支和需求目录。澄清完成后把 FEAT 建议、范围和不做的结论整理给用户，请他在数字员工里发起 init 进入 G0；本 skill 继续完成治理仓登记（下一步）。
- **跨服务需求（L3/L4）**：还要在治理仓 `../sdd-governance/` 里从同名目标分支拉出同名 feature 分支，后续的全局 spec、design 和 prd-index 登记都写在治理仓的这个分支上。
- **单服务 L4**：`design.md` 必备，写在服务仓的需求目录里。

完成标准：用户确认了档位和目标版本；跨服务需求的治理仓分支已就绪；L2～L4 涉及的服务都已在 feature 分支上。

### 3. 分配 FEAT，登记 prd-index

L2～L4 需求执行：

- 把需求拆成需求点，每个需求点分配一个 `FEAT-xxx`（接续治理仓 `prd-index.md` 里已用的最大序号），每个 FEAT 确定归属服务。单一需求点的小需求只有一个 FEAT。
- 在治理仓的 `prd-index.md`（feature 分支上）追加条目：需求单号、FEAT、需求点一句话、需求系统链接、归属服务、状态"进行中"。条目交给用户确认。
- L1 需求不登记 prd-index。
- 平台仓：FEAT 建议同样登记进治理仓；服务仓内的正式 FEAT 绑定由平台 G0/G1 在 spec.md 里落（平台仓的 prd-index 维护以平台为准，治理仓登记不重复维护服务仓副本）。

完成标准：用户确认了 FEAT 拆分和归属。

### 4. 拷问需求

调用 Skill 工具两次，分别运行 `sdd-interview` 和 `sdd-domain`：前者按决策树逐轮提问，后者在提问过程中维护术语表和 ADR。

后端微服务需求里最容易漏的几类问题，要确保决策树覆盖到：

- 异常与并发：重复请求、并发修改、下游超时或失败
- 跨服务：调用顺序、同步还是异步、一致性怎么保证、谁先上线
- 数据：表结构变化、历史数据要不要迁移
- 范围：哪些明确不做

某个决策需要产品或业务方来定、当场问不到时，记下来，建议用户用 `/sdd-questionnaire` 整理成问卷；其余问题继续推进。

### 5. 结束

决策树里没有未决问题时，用几行话总结共识：档位、涉及服务、FEAT 拆分、关键决策、不做什么，请用户确认。

完成标准：用户确认共识完整。然后提示用户在同一个会话里运行 `/sdd-spec`。
