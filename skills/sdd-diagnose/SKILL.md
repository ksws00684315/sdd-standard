# 诊断疑难 bug

一套分阶段的诊断纪律。只有在理由明确时才跳过某个阶段，并告诉用户理由。

读代码时先读相关服务的 `GLOSSARY.md` 和 `docs/adr/`（如果有），建立对相关模块的正确认识。

## 脱敏

这个流程会展示命令、输出和抓到的数据。展示之前**先脱敏**：密钥、token、密码、手机号、身份证号等一律替换为 `<REDACTED>`。复现脚本里的凭证从环境变量读取，不写进展示的内容。抓到的请求带有鉴权头时，只引用有诊断价值的那几行。

脱敏后的信息不足以诊断时，告诉用户，请用户提供。

## 阶段 1：建立反馈循环

**这是整个流程的核心。** 只要有一个对**这个** bug 会变红的、快速的通过/失败信号，就一定能找到原因；二分、验证假设、加日志都只是在消耗这个信号。没有它，盯着代码看多久都没用。

在这一阶段投入不成比例的精力。

### 构造方法（大致按优先顺序）

1. **失败的测试**：在能触达 bug 的接缝上写，单元测试、`@SpringBootTest` 集成测试都可以。
2. **curl 或 HTTP 脚本**：对本地启动的服务发请求，断言响应。
3. **重放真实数据**：把线上抓到的请求、MQ 消息或日志里的入参保存成文件，在本地单独走一遍出问题的代码路径。
4. **一次性测试桩**：只启动出问题的那部分（一个服务，依赖用 WireMock 或测试库），用一次方法调用触发 bug。
5. **随机输入循环**：bug 表现为"有时结果不对"时，用大量随机输入跑，找出失败的模式。
6. **二分脚本**：bug 出现在两个已知状态之间（两个 commit、两个版本、两份数据）时，把"切到状态 X → 检查"自动化，然后用 `git bisect run` 跑。
7. **差异对比**：同一个输入分别跑旧版本和新版本（或两套配置），对比输出。
8. **人工参与的脚本**：最后的手段。必须有人操作界面时，复制 `scripts/hitl-loop.template.sh` 改成具体步骤，让脚本引导用户操作并收集结果，循环依然是结构化的。

### 收紧循环

有了循环之后，把它当成一个产品来打磨：

- 能不能更快？缓存准备工作、跳过无关的初始化、缩小测试范围。
- 信号能不能更精确？断言具体的症状，而不是"没有报错"。
- 能不能更确定？固定时间（注入 `Clock`）、固定随机种子、隔离数据、屏蔽网络。

### 偶发 bug

目标不是一次干净的复现，而是**提高复现率**：把触发动作循环 100 次、并发执行、加压、缩小时间窗口、插入 sleep。复现率 50% 可以排查，1% 不行，就继续提高直到可以排查。

### 确实建不起循环时

停下来明确说明，列出试过的方法，向用户要以下之一：(a) 能复现问题的环境的访问权限；(b) 脱敏后的现场数据（日志、请求记录、线程 dump、带时间戳的录屏）；(c) 在生产环境临时加诊断日志的许可。**没有循环，就不进入假设阶段。**

### 完成标准

能说出**一条命令**（测试命令、脚本路径或 curl），并且已经至少运行过一次（展示命令和脱敏后的输出），它满足：

- [ ] **能变红**：走的是真实的 bug 代码路径，断言的是用户描述的那个症状，修好后会变绿。
- [ ] **确定**：每次运行结论相同；偶发 bug 则有固定且足够高的复现率。
- [ ] **快**：秒级，而不是分钟级。
- [ ] **能自动运行**：不需要人参与；需要人参与时，通过 `scripts/hitl-loop.template.sh` 进行。

如果发现自己在这条命令出现之前就开始读代码、构建理论，**立即停下**：直接跳到假设，正是这个流程要避免的错误。

## 阶段 2：复现并最小化

运行循环，看着它变红。确认：

- [ ] 失败的现象就是**用户**描述的那个，而不是附近另一个碰巧出现的错误。复现错了 bug，就会修错地方。
- [ ] 多次运行都能复现（偶发 bug 则复现率足够高）。
- [ ] 记录下确切的症状（报错信息、错误的输出、耗时），后面用来验证修复。

然后把复现场景缩到**最小、仍然会变红**的程度：输入、调用方、配置、数据、步骤，一次去掉一个，每次去掉后重新运行循环，只保留对失败有影响的部分。最小复现能缩小阶段 3 的怀疑范围，也会成为阶段 5 干净的回归测试。

完成标准：剩下的每个元素都有影响，去掉任何一个，循环都会变绿。

## 阶段 3：提出假设

在验证任何一个之前，先提出 **3～5 个按可能性排序的假设**。只提一个，容易被第一个看起来合理的想法套住。

每个假设都必须**可以被证伪**，写明它的预测：

> 如果原因是 <X>，那么改变 <Y> 会让 bug 消失 / 改变 <Z> 会让它更严重。

说不出预测的假设只是感觉，要么去掉，要么改得更具体。

**验证之前，把排序后的假设列表给用户看。** 用户常常有领域知识，能立刻调整排序（"我们刚改过第 3 个相关的代码"），或者知道哪些已经排除了。用户暂时不在时，按你的排序继续，不用等。

## 阶段 4：加观测手段

每个观测手段都要对应阶段 3 的某个预测。**一次只改变一个变量。**

工具的优先顺序：

1. **调试器或 Arthas**（`watch`、`trace`、`stack`）：一个断点或一次 `watch` 胜过十行日志。
2. **有针对性的日志**：加在能区分不同假设的边界上。
3. 不要"到处打日志然后 grep"。

每一行调试日志都加上唯一前缀，比如 `[DEBUG-a4f2]`，最后清理时 grep 一次就能全部删掉。

**性能问题另走一条路**：日志通常帮不上忙。先建立基线测量（计时、JFR 或 async-profiler 采样、慢 SQL 的 `EXPLAIN`），再二分。先测量，后修复。

## 阶段 5：修复并补回归测试

在修复**之前**写回归测试，但前提是存在**正确的接缝**。

正确的接缝，是指测试能重现调用现场真实的 bug 模式。如果唯一可用的接缝太浅（bug 需要多个调用方，测试只有一个；bug 依赖一条调用链，单元测试复现不了这条链），在那里写的回归测试只会带来虚假的安全感。

**如果不存在正确的接缝，这本身就是一个发现。** 把它记下来：是代码结构让这个 bug 无法被测试锁住。在收尾时告诉用户。

存在正确的接缝时：

1. 把最小复现改写成该接缝上的失败测试。
2. 确认它失败。如果是通过改代码或测试数据强行制造的失败，先和原始版本 diff，确认改动确实生效了。
3. 修复。
4. 确认测试通过。
5. 用阶段 1 的循环，对原始（未最小化的）场景再跑一次。

## 阶段 6：收尾

宣布完成之前必须做到：

- [ ] 原始复现不再出现（重新运行阶段 1 的循环）
- [ ] 回归测试通过，或者已经说明为什么没有合适的接缝
- [ ] 所有 `[DEBUG-...]` 日志已删除（grep 前缀确认）
- [ ] 临时脚本和测试桩已删除，或者移到了明确标注的调试目录
- [ ] 最终被证实的假设写进 commit 或 MR 描述，让下一个排查的人能学到
