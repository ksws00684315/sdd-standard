# 整理问卷

用户手上有一个自己回答不了的问题，答案在另一个人那里（产品经理、业务方、其他服务的负责人）。把它整理成一份 Markdown 问卷，交给那个人异步填写，或者开会时一起填。

**只问"发给谁、要什么"，不问问题本身。** 只向用户问他一定能回答的两件事：问卷发给谁，需要拿回什么。问卷里的问题，瞄准的是"对方知道、而用户需要"的那部分信息。

## 步骤

### 1. 发给谁

一次问清：对方的角色、专业背景、和用户的关系。这决定问卷的语气，以及需要补充多少背景。

完成标准：知道对方是谁，以及对方掌握哪些用户不掌握的信息。

### 2. 需要拿回什么

一次问清：用户自己定不了、需要对方给出的具体决策或事实。

完成标准：得到一份具体清单，写明用户拿到答案后要能做什么、决定什么。

### 3. 写问卷

按下面的结构写，问题瞄准前两步确定的信息差。

保存位置：

- 和某个 SDD 需求相关时，放在该需求的变更目录下：`<服务>/docs/changes/<需求目录>/questionnaire-<主题>.md`。收到答案后，把结论并入 spec，问卷保留作为来源记录。
- 其他情况放在当前目录：`questionnaire-<主题>.md`。

告诉用户文件路径。问卷可以直接发 Markdown，也可以粘贴到飞书文档里发给对方。

完成标准：文件已写好，第 2 步清单里的每一项都有对应的问题。

## 问卷结构

这是一份**探查式问卷**：用户缺少信息，对方掌握信息。问题按重要程度排序，因为异步填写可能只有一次机会；问题超过几个时，按主题用 `##` 分组。

```md
# <问卷标题>

**目的：** 为什么要做这份问卷，取决于答案的是什么决定。

**发起人：** <用户>　**填写人：** <对方>　**答案的用途：** <答案会用在哪里>

## 背景

一段话，让没参与讨论的人也能看懂、答好。够用就行，不要写成一页。

## 填写说明

截止时间和大致耗时。部分回答和"不知道"同样有用：拿不准的请标注出来，不要跳过。

## <主题>

### <问题>

_为什么要问：<只在问题可能被误解、或容易被随手应付时才写这一行>_

>

## 其他

还有什么我们没问到、但应该知道的？
```

每个问题只问一件事，不要复合问题；问题下面直接留出作答位置。
